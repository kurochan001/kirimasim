# 32入力を超えるUDPの評価

[English](wide-udp-inputs.md)。実装：`52652eb`、2026-10-24。

frontとSIR検証器が32入力を超えるUDPを一律に拒否する制限を外し、共有評価器とVMの
入力転送を固定長バッファだけに依存しない形へ改めました。既存のVALUE_SEMANTICS 5.9・
SIR_SPEC 4.3・5.5に従う変更で、意味の修正・依存の変更・診断の無効化はありません。
IEEE 1800-2023の29.3.2は実装上限を認め、組合せで最低10入力、順序で最低9入力を
要求します。10/9が規格上の最大ではなく、以前のヘッダの説明は誤りでした。

## 表現と動作

既存の`udp`・`udp.seq`の引数の意味を保ちます。入力数は既存SIRの正のカウントで表し、
順序UDPの引数数の検査を64bitで計算して、巨大な数の2倍が小さな数へ回り込むのを防ぎます。
コンパイル済みのエッジの列番号も符号付き64bitにしました。

共有カーネルの`udpOutputRead`・`udpStepRead`は、呼び出し中に値が変わらないgetterで
入力を読み、配列の動的確保をせずに既存の表を評価します。ZはXに正規化します。
順序UDPでは、処理済みの端子を現在値、後の端子を以前の値として読むprefixビューを使い、
承認済みの端子順を保ちます。先のエッジが未来の入力変化を見ません。level行の優先と、
一致行がないときのXも既存規則です。

VMは値の転送を担当し、32入力以下には小さなローカルバッファを残しました。それより大きいUDPは
getterを使います。表の一致と
状態遷移はカーネルが所有します。新しい領域・余分なプロセス・可変大域状態・外部ABI変更は
ありません。公開ヘッダはC++20です。従来のポインタAPIは残し、削除した`kUdpMaxInputs`を
使っていたC++呼び出し元は`UdpTable::inputs`から必要な転送サイズを決めます。
評価器自体に可変長の作業用確保は不要です。

## ソースと独立した値の検証

[独自106ソース](../../tools/gen_wide_udp_matrix.py)は、31/32/33/63/64/65/127/128/129/257入力、
module・generate・interfaceの信号・programの刺激・プリミティブのinstance配列を扱います。
組合せは後方の列、0の優先、X/Z、`b`を、順序は初期化、列挙/未列挙の変化、後方の
data/clock、保持、回復を検査します。遅延付き4本は初期出力と後の配送、別の1本は
weakなUDP出力とstrongなドライバを検査します。

現nativeは106本すべてモデルと一致します。保持した旧nativeソース`c6d9c3d`（表示`392687e`）
では20本成功、86本が未対応でした。両参照とも25本一致、コンパイル拒否21本、出力の差40本、
実行失敗20本です。失敗や差で承認済みのUDP規則を置き換えません。
[可搬的な記録](../measurements/2026-10-24/wide-udp-source-validation.json)にソース・期待値の
ハッシュと各エンジンの結果を保ちます。

新しいユニット5件で、独立したSIR/VMと検証器、valsemとの比較、境界列、level行、
X/Z正規化、端子の処理順を検査します。直接のkernel/参照評価は65,537入力も扱いますが、
その入力数のソースをコンパイルしたという意味ではありません。巨大な順序UDP引数数の
オーバーフローも独立して検査します。

[コンパイルした誤実装4種類](../measurements/2026-10-24/wide-udp-negative-controls.json)は、
front上限の再導入、VM入力の折返し、後続入力の先読み、広い入力のZ正規化欠落です。
従来のUDPユニット4件は各誤実装で通り、新ソースの実stdoutか、新しい広幅値の検査が
検出します。判定器の自己検査は数えません。`tools/mutants.py`にも登録し、既存のlevel行の
誤実装定義を新しいヘルパーへ追従させました。

nativeソース`52652eb`と件数/誤実装登録の追従を含むローカルCIは全項目通過しました
（2026-10-24）。dev・ASan・UBSanは各3,317件中3,315件成功、既知の2件のみスキップです。
releaseは3,318件中3,316件成功、同じ2件のみスキップです。Tools 136件、新規106ソース、
ユニット5件が通り、releaseフラグ、禁止事項、SPDX、suiteファイル、大域状態、期待値保護、
README件数、clang-format・clang-tidyも成功しました。既存suiteの本体・期待値・性能回数・
SIR出力29件は変えていません。

## ソースのコンパイルに残る境界

多数の保持行を持つ表は、固定したslangのフロントエンドで検査時間が増える問題があります。
網羅性検査は具体的なエッジ/入力の組合せを列挙し、十分な欠落例を見つけるか完了するまで続きます。
先の端子が広く覆われていると、後方の未定義な組合せへ進む前に時間がかかります。
[独自の時間上限付き観測](../measurements/2026-10-24/udp-edge-coverage-observations.json)では、
ある系統の3/5/9入力のparseは終了し、13/17/33入力では2秒の上限に達しました。
終了しないことの証明ではありません。33入力では参照の実行値にも差があるため、
コンパイル観測を承認済みのシミュレーション期待値にしてはいけません。

元の密な54ソースはハッシュを残し、通常suiteとは別に再生成できます。

```sh
python3 tools/gen_wide_udp_matrix.py \
  --dense-sequential-repro-dir build/udp-coverage-repros
```

これらをsuite通過の証拠にはしません。実行できる行列では列挙/未列挙のエッジを検査し、
警告を無効にしたり依存を改変したりしていません。別の密な33入力のプローブは両参照で通り、
nativeでは比較用subprocessの15秒上限に達します。[上流Issue案](slang-udp-coverage-issue-draft.md)に
再現方法をまとめます。

固定した実装は[slangのMemberSymbols.cpp](https://github.com/MikePopoloski/slang/blob/3b351a52b15755b896d3b0144ae0432547d86618/source/ast/symbols/MemberSymbols.cpp#L1212)です。
上流mainの同ヘルパーも読みましたが、新しい上流版をインストール・ビルドしていません。
多入力UDPソース全体の対応は未確認です。

## 比較の範囲

87件の一覧へ、両参照とnativeで通る組合せ/順序UDPと、密な表のコンパイル境界を加えました。
以前の84件の状態と通過した比較出力は同じです。拡張後の旧baselineの差分27/33件に対し、
現nativeは13.0/開発版で25/31件です。以前の84件での24/30件も当時の集まりとして保ちます。
新たに棚卸しした2件を解消し、別のコンパイル上限を記録したもので、既存の差分やP1全体を
完了したとは扱いません。参照不一致4/7件は同じです。
