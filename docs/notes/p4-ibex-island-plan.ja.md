# Ibex の島の実行費用と変更の測り方

[English](p4-ibex-island-plan.md) · 2026-11-28。実測に使ったビルドを以下に示す。実装順序と [Wire の仕様差分](p4-single-driver-wire-review.patch)は**提案・承認待ち**。

## 実測した出発点

Apple M5 Max で実装 `4fa11d58` の 2 値 native を温キャッシュで5回実行した中央値は **9.706963 秒**。単一スレッド Verilator 5.054 は **0.102895 秒**で、速度比は **1.060%**。ファームウェアは 433,198 サイクルで終了コード0、CRC は e9f5/e714/1fd7/8e3a/e714 で一致した。native のホスト実行命令数の中央値は 220,627,406,087、**シミュレーション1サイクルあたり509,299命令**。この比較先で **1.40%** に達するには **7.350秒以下**、すなわち **24.28%の時間短縮**が必要となる。4値の実行時間も固定したP4開始時ビルドの **1.05倍以内**に保つ。[各回の実測・ハッシュ・設定・負荷](../measurements/2026-11-28/ibex-two-islands.json)・[完了条件](../spec/PERFORMANCE.ja.md)

macOS 27.2.1 arm64、Apple Clang 21.0.0、本体 Release は `-O3 -DNDEBUG -ffp-contract=off`、生成 C++20 は `-O2 -fPIC -shared -fno-exceptions -fno-rtti -ffp-contract=off -fno-fast-math`。保存 SIR に `--tier=native --state=2 --max-scc-iter=65536` を指定し、ウォームアップ1回後、実行順を交互にした。1分負荷は4.60 → 4.44。参照側はP3と同じ設定とファームウェアを使った。[入力と再現手順](p4-performance-profile.ja.md)

島のメンバー評価130,473,903回はすべて個別の生成C++を呼び、融合経路は0回だった。次の内訳は保存SIR上の書き手を分類した値である。直接書き込みの適格判定には、後述のネットの証明も必要となる。

## 242島で、なぜ1サイクルに約156回起床するか

[静的解析](../../src/analysis/islands.cpp)は、適格な書き手の**即時の書き込み**と読み手の感度範囲が同じ物理スロット上で重なると両者を結ぶ。クロック駆動の適格プロセスは物理トリガの範囲とエッジが一致する場合も結ぶ。組み合わせ回路は入力を共有するだけでは結ばれず、NBAは後続リージョンで反映される。解析対象外のプロセスも島に入力できる。このSIRでは77件の CombAt が島の外で動いた。階層をまたぐ場合も同じ規則で島を分ける。

833メンバーのうち**187件が単独島**で、すべて連続代入だった。うち65件はポート接続で、187件のうち**101件はトリガ列が空で各1回しか動いていない**。残る55島のサイズ別の個数は、2が33島、3が9島、4が3島、5が6島、8が2島、78と417が各1島。単独島全体の評価は7,013,091回（16.19回／サイクル）だった。

[スケジューラ](../../src/kernel/sim.cpp)の `proc.wakeups` は、島のバッチを実行したときと通常プロセスを再開したときに増える。該当する final・Postponed の起動も対象となる。Ibexの2値では次の内訳になった。

| 433,198サイクルで数えたもの | 総数 | 1サイクルあたり |
| --- | ---: | ---: |
| 論理上の起床 | 67,577,682 | 156.00 |
| 島のバッチ実行（`island.evals2 + island.evals4`） | 41,593,458 | 96.01 |
| 残りの起床（差分） | 25,984,224 | 59.98 |
| バッチ内のメンバー評価 | 130,473,903 | 301.19 |

複数メンバーの起床が同じバッチに入る。別の島、起床フェーズの違い、途中に入った通常のActiveイベントはバッチを分ける。値が再度変われば同じ島がまた起床する。島外の生成 CombAt だけで24,684,622回（56.98回／サイクル）呼ばれた。島をまとめても、この通常プロセスの呼び出しは残る。

**まとめる余地。** 単独島の5件はSIR上で同じスロット778にガードなしの同じトリガを持ち、各440,217回動いた。全通知が同時に並ぶ理想条件でも、この5件で省ける物理ディスパッチは最大 **1,760,868回（4.06回／サイクル）**。有効なビット感度、実際のキュー上の隣接と節約量は未確認。まず発火した範囲・エッジ、時刻、リージョン、フェーズ、待ちの世代と順序、隣のキュー項目、バッチが分かれた理由を記録する。実行中に末尾に追加される通知も含め、参照実行の順序を再現できる連続区間だけをまとめる。別のActiveイベント、観測者、クロック待ち、NBA境界を追い越さない。時刻0、失効した待ちの取消し、SCCの反復、割り込みまでに完了した処理、論理カウンタを保つ。物理的な取り出しとバッチ数は別に数える。共通入力の読み手の間に通常の待ち手を挟む例、互いに離れたスライス、異なるクロックで照合する。島をまたぐ統合は独立した後続実験とする。

## 大きな島に広げる前に直す箇所

1. **借用直前の検証を領域単位にする。** 現在の `evaluateCombGroup` は全メンバーの観測世代・監視・module path と、待ちの有効性を調べる。バインド時に物理スロットと関連する待ち・エイリアスから影響先の全領域への逆引きを作る。購読の変更、動的順序、共有する待ち、監視・module path の登録解除、force、波形、外部からの観測で領域の世代または無効フラグを更新する。すべての変更入口を列挙し、競合、VPI、保留中のNBA、clocking、キュー状態の大域判定は残す。観測が有効になる前に無効化されることを示せれば、観測検査は世代比較1回にできる。不一致・飽和時は従来経路を使い、再利用前にホットパスの外で再検証する。待ちの有効性は未登録・保留・資源保有の件数や dirty 項目の世代で別に管理する。遅い登録・解除、世代飽和、再入、独立した2つの Context を試す。
2. **dirty 項目から段を直接引く。** バインド時にプロセスIDから領域と順位への表を作り、dirty 項目ごとの `find_if` を世代付きO(1)参照に置き換える。組み合わせ回路のレベル・SIR順、クロック駆動の待ちの通知順、カーネルのバッチ境界を保つ。失効・重複・未登録・到着順が逆の項目を試す。
3. **影の記憶域を照合対象に絞る。** `startFusionCheck` は評価のたびに2つの記憶域全体を複写し、終了時にも全体を比較する。エイリアス、部分読み、ガード、a/b 両プレーンを含む読み書き可能な物理ワードの集合を事前に求め、重複を除く。記述子のオフセットを照合用の2つの小さい配列に割り当て、呼び出しごとにこの範囲を複写・最終照合する。影の生成コードのアクセスと参照VMの書き込みを証明済みの範囲に制限し、範囲外へ書いて元の値に戻す誤りも検出する。エイリアス、無関係な実状態、同値・変化ありの書き込み、範囲外書き込みの故障注入を試す。隔離を証明できなければ影の実行前に従来照合へ戻す。開始後のあふれ・不一致は失敗とし、実状態にはVMだけが反映する。通常実行版には記録コードを生成しない。
4. **複数領域と複数ワードの起床集合にする。** 現状は `emitFusion` と `prepareCombGroup` が設計全体のメンバー表を見ており、VMは無関係なプロセスにも条件を課す。スケジューラはグループを1つだけ保持し、サービス19 v1の ready・visited・読み手マスクは各64ビット。島・バッチから領域ごとの決定的な記述子を引く方式とし、領域外の全読み手・書き手も考慮して適格性を判定する。記述子表、長さ付きの複数ワード集合、疎な後続リストにはサービスの新しい厳密な版を提案する。v1の読込みを保ち、生成器・キャッシュの版と通常／照合を区別する。非空ワードを順位順にたどり、待ち順序の桁あふれ判定には実際の上限を使う。借用の寿命と割り込み順は維持する。ABIの差分は実装前に別途レビューする。63/64/65、127/128/129件、複数領域、適否混在、疎・密な伝播、起動時、SCCの従来経路を検査する。

まず現行の小規模領域と規模を変えた対照回路で検証する。診断実行で全員走査数、dirtyの表引き数、影で複写・比較したワード数、ヒープ操作、物理的な待ちの再登録数を記録する。多数の休止メンバーのうち1件だけ起こす場合、定常時の通常実行では観測検査は定数回、順位参照は1回とする。無関係な記憶域を増やしても影のワード数は増えないことを確かめる。Ibexの大きな島に適用する前に、`comb_chain` と `hierarchy_fanout` で従来経路も含めて再検証する。

## 承認後の最初の実験

同じRelease設定で4つの計測専用ビルド（またはコンパイル時の切り替え）を用意する。汎用の非巡回 Cont の適格証明、対象範囲、演算本体、記憶域配置、観測境界をそろえる。417件のうち証明済みの部分領域だけを扱い、共有宛先の非重複108件と重なり得る2件は従来経路に残す。同じ島で適格にならないメンバーのキュー上の位置を保つ。境界を分離できなければそのバッチは従来経路を選び、理由を数える。島0とNBAには現行経路を使う。島番号は集計だけに使い、本体の条件に入れない。他にも適格な領域があれば、その変化は分けて計上する。まず両方の最適化を切った共通基盤と `4fa11d58` を比べ、基盤自体の影響を測る。

| 条件 | 物理書き込み・通知 | スケジューリング・待ち |
| --- | --- | --- |
| 00 対照 | 従来のカーネル書き込み | 従来の呼び出し・ヒープ・再登録 |
| W 書き込みのみ | 証明済みの直接書き込みと変化検出。同じ位置で同じ待ちを通知 | 00と同じ呼び出し・ヒープ・再登録 |
| S スケジューリングのみ | 従来のカーネル書き込み。元の位置で観測者に通知 | 順位付き起床集合、順序を保つ呼び出し、証明済みの内部再登録 |
| WS 両方 | Wと同じ | Sと同じ |

書き込みからキューへの引き渡しは参照経路の契約に従う。Wだけなら従来のメンバー呼び出し内でホスト側の書き込み処理を短縮できる。Sだけなら、従来の書き込みが実際に起こした内部の待ち手を新しい実行順制御に渡し、同期・外部観測者には従来どおり通知する。ポインタの借用中にホストへ再入しない。外部イベントが割り込む可能性がある場合は、借用前に分割または従来経路を選ぶ。4条件の適格判定をそろえ、実際の適用率・フォールバックの差も報告する。

- 前述のSIR、ファームウェア、OS、コンパイラとフラグ、参照バイナリ、各キャッシュの識別子と負荷上限（18コアで1分負荷9以下）を固定する。各キャッシュ準備後、4条件の順序を均等に入れ替え、逆順も含めて各5回以上の有効な測定を採る。前後の負荷、生の秒数と実行命令数、バイナリハッシュ、ばらつきを残す。macOSでは[既存の再現ツール](../../tools/coremark_profile.py)と同様に本体プロセスを `/usr/bin/time -lp` で測る。コンパイルと診断は別実行とする。
- 各条件で**ホスト実行命令数の中央値÷433,198**と絶対秒数の中央値を報告する。削減量は 00−W、00−S、00−WS、相互作用は (00−WS)−(00−W)−(00−S)。別の計装実行で島4の費用内訳、キュー操作、従来経路に戻った理由、Wireの証明が成立した書き込みの割合を出す。3通りの実験結果はすべて未計測。
- CRC 5個と433,198サイクルの一致、両状態モードでVMとの効果の順序照合、既存の論理PerfCountの一致、観測と割り込みの検証を通す。低負荷の4値の絶対時間は固定したP4開始時ビルドと比較する。命令数が減っても時間短縮が再現しなければ速度向上とは判定しない。
- WSの実測で残った時間から島0の予算を決める。クロック駆動の順序付き起動、次に連続した遅延0のNBA発行を別々に試す。Activeで右辺と添字を取り込み、NBAで発行順に反映し、島外の発行者・部分重複・観測順を保つ。島0のNBA発行制御はすべて合わせて約6,005命令／サイクル。各段階でIbexを完走させる。なお不足すれば、境界の書き込みと島外の通常の CombAt に残る費用を測り、次の変更を選ぶ。

## 島の構成と起床回数の再現

`264ad2ce` で診断を再実行し、標準出力、カウンタ、静的な島レポート、全tier行と空の融合レポートが保存記録とバイト単位で一致することを確認した。[プロファイル](p4-performance-profile.ja.md)の固定SIRとファームウェアのパスを指定して実行する。

```sh
mkdir -p build/ibex-plan-check
build/release/src/driver/kirimasim --load-sir="$IBEX_SIR" --tier=native --state=2 \
  --cxx=/usr/bin/c++ --cache-dir=build/ibex-plan-check/cache --max-scc-iter=65536 \
  --stats=json --report-islands=build/ibex-plan-check/ibex.islands \
  --report-tier=build/ibex-plan-check/ibex.tier.jsonl \
  --report-fusion=build/ibex-plan-check/ibex.fusion.json "+image=$COREMARK_HEX" \
  +cycles=443198 > build/ibex-plan-check/ibex.stdout
```

tierレポートの `island` がnull以外の行を島ごとに集め、行数を島の大きさ、全件nativeのこの入力では `native_calls` の和を評価回数とする。`process_id` でSIRの行と対応させ、種類・トリガ・書き込み範囲を読む。起床の内訳は標準出力の末尾のJSONから計算できる。速度は別実行の5回で測った。
