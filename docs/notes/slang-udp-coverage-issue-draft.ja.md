# 投稿案：幅広 UDP のエッジ網羅検査がコンパイルの時間上限を超える

[English](slang-udp-coverage-issue-draft.md)

状態：**草稿・未投稿**、2026-10-24。slang への報告案です。slang のコンパイル診断に関するもので、
網羅性の診断を保ちながら検査をスケールさせることを求めます。警告の抑止や UDP の実行時の意味の変更は求めません。

## 観測環境

- kirimasim が固定して使う、未改変の slang コミット `3b351a52b15755b896d3b0144ae0432547d86618`。
- macOS/arm64、AppleClang 21。既存のコンパイラ・runtime のバイナリを使いました。
- slang の driver を使う kirimasim の `parse` から観測しました。単独の slang ツールはビルドも検証もしていません。
- コンパイラ警告の抑止、依存のパッチ適用はしていません。MIT ライセンスの依存である slang 以外のシミュレータのソースも読んでいません。

最初の端子の正・負エッジは既知のデータ値を選び、不明なデータの遷移は X を返します。
他の端子には保持行があります。具体的な単一入力のエッジを網羅する小さな表を意図し、
大きな生成設計ではありません。問題はコンパイル中、kirimasim の UDP 命令への変換より前に起きます。

観測したコマンド：

```sh
kirimasim parse --top=top udp_coverage.sv
```

この parse は外部から設定した 2 秒の上限に達し、native のコンパイル・実行も比較の外部上限 15 秒に達します。
Icarus 13.0 stable と 14.0 開発版は、どちらもこの例をコンパイル・実行して `1` を表示します。
単独の `slang --top top udp_coverage.sv` は、保守者向けに提案する独立した再現手順で、ここでは未実行です。

## 原因箇所と測定

dense な 65 入力の parse をサンプリングしたところ、`PrimitiveSymbol::fromSyntax`、
`checkPrimitiveEdgeCombinations`、`BitTrie::contains` 内にいました。
[固定版のヘルパー](https://github.com/MikePopoloski/slang/blob/3b351a52b15755b896d3b0144ae0432547d86618/source/ast/symbols/MemberSymbols.cpp#L1212)
は具体的な入力・エッジの組を列挙し、不足例が十分見つかるか、検査が完了するまで続けます。
前の入力が広く網羅されると、後の端子の不足例を探すまでに時間がかかり得ます。
診断を保つ記号的な網羅検査など、スケールする手法が役立ちます。

別の独自ファミリーでは、3/5/9 入力の parse は完了しますが、13/17/33 入力は 2 秒の上限を超えます。
これは観測した上限であり、停止しないという主張ではありません。33 入力で参照側の実行結果が異なる点は
コンパイル問題とは別で、その値を slang の期待値として提案しません。
[可搬的なソース・ハッシュ・測定](../measurements/2026-10-24/udp-edge-coverage-observations.json)を参照してください。
独自の dense 変種 54 件は次で生成できます。

```sh
python3 tools/gen_wide_udp_matrix.py   --dense-sequential-repro-dir build/udp-coverage-repros
```

[Issue #936](https://github.com/MikePopoloski/slang/issues/936) は元の網羅性要件に関するもので、
クローズ済みです。リポジトリの issue を UDP で検索し、その issue と無関係な型・再定義の 2 件が見つかりましたが、
重複がないと証明するものではありません。現行の上流ヘルパーのソースは確認しましたが、
新しい上流バイナリはインストールも検証もしていません。

この草稿はローカルでレビューできます。issue やコメントは送っていません。
