# VPIの次時刻コールバック：無視する値と読み取り専用領域での登録

[English](vpi-next-time-callback.md) · 2026-11-05。

次時刻のコールバックは、シミュレーションが実際に到達する次のタイムスロットを観測するもので、
遅延の要求との違いは[承認済みVPI契約4](vpi-p1-proposal.ja.md#4-書込みとcallback)で確認できます。

実装`fc2650be`は、この既存契約とSCHEDULER_SPEC 7・17に従い、`cbNextSimTime`の登録を修正します。
コールバック理由・API・依存・意味の改定は追加しません。これはブランチ上の実装記録であり、
mainへの公開やP1完了を示すものではありません。

## 規則と修正

時刻の記述子には`vpiSimTime`または`vpiScaledRealTime`を指定します。数値の値は無視し、
整数の0・最大値、実数の有限値・負値・無限大・NaNは遅延を要求しません。
記述子はコールバック実行時に返す時刻の形式を選び、その形式のフィールドだけに意味があります。
時刻の記述子がない場合、抑制形式、未知の形式は、従来どおりAPIエラーです。

以前は共通の分岐でこの値を遅延に変換していたため、負値や非有限の実数で、誤った時刻の
オーバーフローとして実行を終了する場合がありました。またPostponedから値0で登録すると、
同じタイムスロット内の処理を要求するものとして拒否していました。
実際には後のタイムスロットを待つため、読み取り専用のコールバックから登録しても、
同じタイムスロット内のイベントを追加するものではありません。

記述子の検査を`Vpi::Impl::timeFormat`にまとめました。通常の遅延コールバックと書込みは、
さらに`Vpi::Impl::delay`を通り、数値の検査・丸め・オーバーフローの動作を保ちます。
`vpi_register_cb`は次時刻の観測では形式だけを検査し、task呼出し・timerコールバック・
読み取り専用コールバックを同じ入口で扱います。実行は次の実際のスロットのPre-Activeで1回だけです。
観測自体は将来のスロットを作らず、静止を妨げません。登録時の記述子のコピーと取消しも保ちます。

## 独立した検証

[比較記録](../measurements/2026-11-05/vpi-next-time-comparison.json)には、独自の144ソースがあります。
ソースの場所6種類×登録段階3種類×値8種類です。場所はmodule・子module・generateブロック・
interface・program・static task、段階はtask呼出し・読み取り専用コールバック・timerコールバックです。
各期待値は、実際のtick 3で1回だけ呼ばれ、時刻が正しく返り、APIエラーがないことを求めます。
pluginはコールバックのobjectにnullを使い、`1ns/1ns`で実行します。objectのscopeで尺度を変える
時刻はContextテストで別に確認します。

固定した`92001039`のrelease実行ファイルは**60/144件**、実装後は**144/144件**が成功します。
明示的に選んだIcarusのコンパイラとruntime **13.0 stable（`v13_0`）**でも**144/144件**が成功し、
同じ独自C pluginとkirimasimが独立に書いたヘッダを使います。
ソースのハッシュと期待出力は変更前後で同一で、プロセスの正常終了だけでは一致と数えません。
既存の188プローブや固定P1母集団とは別の検証であり、除外や、期待値と一致しない結果の合格扱いはありません。

Contextを使う新しい単体テスト5件で、無視する値、実行前・実行中の登録、記述子のコピー、scopeで尺度を変えた時刻、
不正形式、通常のtimerの検査・丸め、読み取り専用領域での登録、取消し、静止を確認します。
関連する**61件のCTest**はdev・release・ASan・UBSanのそれぞれで成功しました。
除外なしのdevは**12,251/12,251件**で、失敗・スキップはありません。
最初の全体実行では追加ジェネレータの件数同期だけが失敗したため、件数を別に更新して全件を再実行しました。
[検証メタデータ](../measurements/2026-11-05/vpi-next-time-validation.json)に、範囲・ソースのハッシュ・
各構成の結果を記録しています。

[コンパイルした3つの対照](../measurements/2026-11-05/vpi-next-time-controls.json)はすべて検出しました。
無視する値を遅延へ変換する誤り、読み取り専用領域で拒否する誤り、実際の次スロットより1 tick遅らせる誤りです。
各対照はビルドに成功し、意味を検査するテストが失敗し、元のソースのSHAを復元しました。
復元後は選択した6テストが再び成功しています。レジストリの1,206箇所が適用可能である検査とは別であり、
1,206変異すべてをコンパイルしたという意味ではありません。関係する4翻訳単位のclang-tidyには診断がありません。

既存のテスト本体・期待出力・アサーション・性能の予算は変更しません。
承認後のpush前には完全なlocal CIが必要です。netの部分・遅延書込み、containerの暗黙感度などの
[P1の境界](../P1_SUPPORT.ja.md)は残作業で、slangへの投稿も保留を続けます。

## 再現

```sh
ctest --preset dev -R '^(VpiNextTime[.]|Vpi[.]|VpiNet[.]|VpiFront[.]|cli/vpi)' --output-on-failure
python3 tests/cli/run_vpi_next_time_tests.py --kirimasim build/dev/src/driver/kirimasim --report build/vpi-next-time.json
python3 tools/gen_vpi_next_time_matrix.py --output build/vpi-next-time-sources
python3 tools/mutants.py --check
```

両方の版の出力を確認してください。どちらのシミュレータのソースも、外部Issueの再現コードも読んだりコピーしたりしていません。
