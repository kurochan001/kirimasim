# MOS・双方向スイッチの調査

[English](mos-switch-investigation.md)。調査日：2026-10-24。

MOS・双方向スイッチのソース実行は**未対応**です。既存の強さ区間のカーネルAPIと、
広い三状態ゲートのsideマスクだけでは、スイッチ網は実行できません。この記録は直近の
独自の観測と設計上の残作業をまとめたもので、承認済みの仕様を変更しません。

## 証拠と限界

[可搬的なソースと結果](../measurements/2026-10-24/mos-switch-design-observations.json)に、
独自28プログラム・コンパイラとruntimeでの56観測を保存しました。各プログラムは、
手元にある次の両方の組でコンパイル・実行とも成功しました。

- Icarus `13.0 (stable) (v13_0)`。
- Icarus `14.0 (devel) (s20260301-411-gca6b8d376)`。

28組すべての標準出力が一致しています。データにはソースのハッシュ、版、コマンド、
終了コード、正確な標準出力があります。他のシミュレータのソースやテストは読んでいません。
この調査データではkirimasimの実行を測っていません。[79項目の機能比較](icarus-13-comparison.ja.md)とは
別の調査で、当初の`57a64ef`では差分が13.0の20件・開発版の26件でした。
その後の[fork比較](fork-local-declarations.ja.md)で現在は81件・差分21/27です。参照の一致だけで
IEEEへの適合や承認済みの期待値は決まりません。性能とLinuxでの動作は再測定していません。

## 実装に必要な仕組み

- **値が同じでも強さが変わる。** `strength_only`では、入力の論理値は1のまま、強さが
  weakからstrongへ変わります。pull-0と競合する下流のMOS出力は0から1へ変わりますが、
  通常の`@(source)`は変更を0回と記録します。内部の強さ依存と、利用者の値変更への
  購読を区別する必要があります。
- **素子固有の真理値と減衰。** `mos_z_unknown`は、データがZ・制御が不確定でも、
  MOS/CMOSの6種類すべてでZを出します。28.7・28.9の規則が必要です。抵抗性の連鎖では
  supply → pull → weak → medium → smallとなり、その後はsmallのままでした。
  非抵抗性の経路ではsupplyがstrongになります。強さの減衰は28.13・28.14に規定され、
  通常の三状態ゲートの真理値を当てはめるだけでは足りません。
- **架空のドライバを作らない受動網。** `root_removed_ring`では、外部ドライバを外すと
  3ノードとも1からZへ変わり、`floating_self`もZのままです。循環した経路だからといって、
  隣の解決値を独立した永続ドライバにしてはいけません。一方、
  `mos_directed_feedback_drop`は外部の駆動を外しても1を保持しました。有向MOSの出力
  ドライバと受動的な双方向経路には、異なる状態・スケジューリングの契約が必要です
  （4.9.5、28.7・28.8）。
- **ポートの同一性と経路の減衰。** `port_supply_identity`では、子の出力から親のbitへ
  supplyの強さを保ち、その後の`tran`でstrongへ減衰します。強さを保つネットポートの
  接続と、スイッチの辺を区別する必要があります（4.9.6、28.13）。

## 詳細な契約のレビューが必要な点

[承認済みの区間モデル](../spec/VALUE_SEMANTICS.ja.md#5-ネットの解決)は既に両端点を
保ちます。全経路での伝播、網の所有権、force、遅延付き全状態の更新には、
[P1_SCOPE](../spec/P1_SCOPE.ja.md)に従って詳細な契約が必要です。

`positive_range`は、不確定なstrong-1ゲートの寄与とweak 1を組み合わせます。
既存モデルではweakからstrongまでの正の入力区間となり、その区間を完全に伝播して
pull 0と解決するとXになり得ます。両参照は出力1を表示しました。原因と規格上の解釈は
**未確認**です。入力の最大の強さだけを見ると情報を失うため、この観測を理由に
承認済みのモデルを無断で置き換えません。

wiredネットの経路を調べた5件は、全ノードが`wand`・`wor`の場合もXを出しました。
局所のwired解決と経路の伝播について解釈のレビューが必要で、この観測を期待値には
採用していません。forceの調査も、ノード自身の強制された読み値と他ノードへの寄与を
区別します。`force_highz_transit`では、通過点をZへforceしても、遠方の1が反対側へ
到達しました。単純に経路を切る方式ではこの観測を再現できません。正確な契約は未確認です。

遅延付き素子の初期状態も別にレビューが必要です。弱い入力・背景ドライバなしでは、
`mos_delayed_start`は初めに`WeH`を表示し、`rmos_delayed_start`は初めに`StX`、後に
`St1`を表示しました。後者では28.14で想定するweakからmediumへの減衰が見えません。
原因は未確認で、初期状態の承認済みの期待値にはしません。既存の
[遅延付き三状態sideの案](delayed-gate-side-proposal.ja.md)も承認待ちで、
それだけですべてのMOS・スイッチの時間規則を定義するものではありません。

実装に先立ち、完全な区間の伝播、複数経路を通る物理ドライバの所有権、不確定な制御、
wiredネットの組み合わせ、force/release、初期化と取消し、強さだけの変更通知、ポート接続、
リソース不足を仕様で決める必要があります。SIRで必要な状態を共有カーネルへ渡し、
ソースの変換やVMでの転送にとどまらず、欠けている実行の意味を実装する必要があります。
この調査で新しい意味を承認したことにはならず、既存の5つの修正案も承認待ちのままです。

## 詳細案と負荷を加えた追試

[全体の実行修正案](mos-switch-proposal.ja.md)で、網、MOS、ポート、force、時間、SIR/kernel、
書式の判断を具体化しました。実装済み機能は増やしておらず、以前の5案も承認待ちです。

[独自18ソースの追試](../measurements/2026-10-24/mos-strength-matrix-observations.json)は、
各MOSを単独出力・weakとの競合・pullとの競合で調べ、各参照で合計2,304スカラー組を
記録します。全射影値は真理値・減衰・局所解決の計算と一致しました。競合ドライバがある
場合は強さの表示も全件一致し、単独の抵抗性出力だけ各参照252組の表示が違いました。
従って、先の単一ドライバの`St1`表示だけでは、解決時にも減衰しないとは言えません。
実装上の原因は未確認で、他のシミュレータのソースは読んでいません。
