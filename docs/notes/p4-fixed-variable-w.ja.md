### 基準値 9.707 秒と 9.865 秒の差

9.706963秒の記録は別スクリプトで標準出力・エラーをパイプに取り、終了まで待っていた。9.864789秒の記録は `62da5eb0` の終了通知式を使用した。このコミットは `coremark_profile.py` のタイムアウト待ちポーリングを取り除いたもので、最初の記録にはそのポーリングがなかった。

同一条件で再ビルドした `4fa11d58` を測るとパイプ式 9.7466 秒、終了通知式 9.7458 秒。W 直前の同一実行ファイルではそれぞれ 9.8593 秒、9.7634 秒だった。直前ビルドの同じ子プロセスについて、ラッパーの壁時計から 0.01秒単位の `time -lp` の real を引いた中央値は、パイプ式 8.7 ms、終了通知式 5.6 ms、旧ポーリング式 46.9 ms。

過去の2記録でも、実時間の差1.63%に対し、命令数の中央値は509,299 → 509,333 命令／サイクル（+0.007%）だった。終了通知式でそろえた4faからW直前までの命令数差は +2 命令／サイクル。同じ終了通知式でのリビジョン間の実時間差は +17.6 ms（過去の差157.8 ms）。両ソース間で `src/` の変更は、保存済み SIR 実行が通らないフロントエンドの randsequence のみ。実行ファイルの配置、slang の固定版、負荷や動作周波数は実時間に影響し得る。P4開始時と Verilator は当時のバイナリそのものを使用した。4fa は当時の固定ソースからの再ビルドでバイナリハッシュが異なる。この比較から、過去の0.158秒を単一の原因に帰することはできない。[4fa の当時のデータ](../measurements/2026-11-28/ibex-two-islands.json)・[W 直前の記録](../measurements/2026-11-28/ibex-pre-w-baseline.json)

## 失効と正しさ

| 回路・条件 | 束縛数 | 失効数 | 失効後に従来経路へ戻った書き込み | 省いた同値書き込み |
|---|---:|---:|---:|---:|
| `ibex` | 1 | 0 | 0 | 125,481,155 |
| `dyn_queue` | 0 | 0 | 0 | 0 |
| `class_pool` | 0 | 0 | 0 | 0 |
| `dynarray_resize` | 0 | 0 | 0 | 0 |
| `force_release` | 0 | 0 | 0 | 0 |
| `variable_site_heap` | 1 | 0 | 0 | 64 |
| `grow-sites` | 2 | 1 | 4 | 4 |
| `force-sites` | 2 | 1 | 4 | 4 |

Ibex は固定 1,136 箇所を1回束縛し、対応する生成本体を 26,974,775 回起動した。変化した 43,855,822 回はすべて従来経路に渡した。型付きヒープでのオブジェクト生成や動的配列の再確保は、カーネルの物理スロット表を増やさない。daily の `dyn_queue` は400万反復。固定した daily にクラスの回路がないため、`class_pool`・`dynarray_resize`・`force_release` は holdout の元の回路を使った。これらは W 対象箇所の実行0回で、結果は VM と一致。補助回路ではクラス生成と動的配列の確保を64反復しながら W を作動させた。`grow-sites` と `force-sites` は1モジュールを2個の Context で共有し、片方だけを失効させた。force の解放後もその束縛は失効したままで、もう片方は利用を継続した。

2値・4値とも変更前後の native の全カウンタが一致した。2値の論理書き込みは 426,247,905 回、変化は 200,803,958 回。全サイクルの `--tier-check` でも CRC、時刻、スケジュールと書き込み件数が一致した。照合版は VM が観測した書き込み直前の値を使い、各試行と独立したカウンタを比較する。同値時の加算を故意に取り除いたモジュールでは検査が失敗した。execute/check のキャッシュ分離は両方の作成順で確認。記憶域表やカウンタ表のコピーは元の束縛から独立し、代入・移動時は影響する借用を先に失効させる。VPI 値変化コールバック、エッジ・iff、$monitor、通常／グリッチ VCD を付けた回路では2値で7回、4値で10回を省き、コールバック出力・論理カウンタ・VCD の遷移が VM と一致した。サービス19の先頭配置が変わる場合はサービス20の版も上げる。版1の失効は束縛の終了まで有効。再束縛または箇所単位の失効はP5前の検討事項に残した。

## 生成コードの比較実験

| 計測専用ビルド | 中央値（秒） | 最小〜最大（秒） | 命令／サイクル | 対照からの削減 |
|---|---:|---:|---:|---:|
| `control` | 9.4688 | 9.295–9.763 | 472,304 | +0 |
| `read` | 9.0856 | 8.990–13.957 | 460,254 | +12,050 |
| `end` | 9.2997 | 9.102–13.342 | 465,485 | +6,819 |
| `read-end` | 8.9350 | 8.886–13.717 | 453,052 | +19,253 |
| `dynamic` | 9.2047 | 9.168–9.686 | 456,541 | +15,764 |
| `inline` | 9.3528 | 9.256–9.489 | 471,009 | +1,295 |

6条件では、この回路の生成本体全体を対象にした。先の読み出し・終了確認の見積もりは島外の CombAt だけを数えていた。今回の6条件は同じ W 本体・固定範囲 W を使い、内部の C++ レイアウトを参照する `-DNDEBUG` も含めコンパイル設定をそろえた。各5回測り、全条件で出力と native の全カウンタが一致した。`read` は固定位置の読み出し先の取得、`end` は書き込み直後の元の位置で同じ終了フラグを調べる処理をインライン化。`read-end` は併用。実行された固定読み出しは 1066.41 回、書き込みなどの後の終了確認は 812.10 回／サイクル。残った間接読み出し・間接終了確認はそれぞれ 0.00・0.00 回／サイクル。実験は Context の C++ 配置を直接使用する。製品化には移植可能な ABI と照合経路のレビューが要る。同期ガードで終了したとき、その後ろの書き込みが実行されないことを両状態で VM および3条件で確認。遅延0の native リングで SIGINT を送ると、全条件で 1 ns に同じ final 出力、終了コード130となった。

`dynamic` は生成コード5箇所で、従来の添字・範囲・クリップ処理の後に同値検査を加えた。1サイクルあたり試行 160.49、同値 145.14、変化 15.35、失効などによる辞退は全実行で 0 回。完全な範囲外では書き込み自体が発生しない。別の小回路で不定、負、境界をまたぐ選択、範囲外の VM との一致を2値・4値で確認した。`inline` は既存の同値判定関数だけを強制インライン化した独立実験。通常ビルドの対象は承認済みの固定範囲まで。

### 変化した書き込み1回の内訳

通常の CombAt について、未計装ホスト上で空の間接呼び出しを差し引いた包含値は **全幅 420.7 命令、部分選択 441.5 命令**（W 前は419.6・441.6）。約1,024回に1回の無作為抽出を3系列で行った。別の一時ホストでは約2,048回に1回、3系列で区間を測った。

| 種類 | ABI・検証／ビット操作・格納／観測確認／購読照合／起床・キュー／ガード・監視／残差 | 計装ホストの包含値 | 固定購読訪問／起床回数 |
|---|---|---:|---:|
| 全幅 | 76.5 / 93.7 / 148.5 / 85.9 / 95.2 / 0.0 / 26.4 | 526.2 | 1.02 / 0.60 |
| 部分 | 76.2 / 94.0 / 157.3 / 147.6 / 43.8 / 0.0 / 31.9 | 550.7 | 2.25 / 0.32 |

区間計装自体が生成されるホストの機械語を変える。空計測分を差し引いても、計装ホストの包含値は未計装より全幅で 105.6、部分で 109.2 命令大きい。残差は計装ホスト内で合計を合わせた値。次の候補は観測の有無を確認する費用と、特に部分書き込みの購読照合。実際に一致する購読の判定、同期した観測、起床順の維持に必要な費用を含むため、ここをそのまま削減量にはできない。

## 再現

[固定した設計・ファームウェア・比較先の準備](p4-performance-profile.ja.md)と、生データで特定した Release ビルドを使う。各条件は `--tier=native --state=2|4 --max-scc-iter=65536 +cycles=443198`。新規ディレクトリにバイナリ・状態ごとにキャッシュを用意し、`--resume` で高負荷分を取り直せる。CI と速度測定は時間を分ける。`--stats=json` と `--tier-check` は別の診断実行。区間ごとの実行命令は macOS の `thread_selfcounts` を使用した。

```sh
python3 tools/compare_ibex_w.py --entry "$ENTRY" --historical "$BUILD_4FA" \
  --before "$PRE_W" --after "$W" --reference "$VTOP" --sir "$SIR" \
  --firmware "$RAM" --cxx=/usr/bin/c++ --out build/replay-ibex-w
"$W" --tier-check --state=2 --max-scc-iter=65536 --load-sir="$SIR" \
  --stats=json +image="$RAM" +cycles=443198
"$W" --tier=native --state=2 tests/context/designs/variable_site_heap.sv
ctest --test-dir build/release -R 'static_islands|emitted_island' --output-on-failure
python3 tools/local_ci.py
```
