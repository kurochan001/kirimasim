# Debug の組み立てでの kernel の不変条件の深い検査

[English](deep-checks.md) · 提案、2026-11-08。1〜3 段目は実装済み。

## なぜ

kirimasim は障害を値で報告します。SIR の関門（`sir::verifyDesign`）はどの組み立てでも動き、VM は
`EndReason::Internal`（driver の終了コード 3）で実行を終え、kernel の各領域は、約束を破る呼び出しにそれぞれの誤りを
返します（ヒープ、活性化レコード、NBA、オブジェクト、文字列、強度、管理イベント、パターン、clocking）。Debug の
プリセットは、slang を slang 自身の assert つきで、C++ のライブラリをその検査つき（`_GLIBCXX_ASSERTIONS`、libc++ の
強化モード）で組み立て、すべてのテストをサニタイザの下でも走らせます。

確かめていないのは、kernel 自身の状態が、守るはずの不変条件を守っているかです。kernel の不具合がそれを破ると、
実行は障害にならずに続き、誤った結果を出します。kirimasim には `assert` がなく、`assert` は合いません。Release の
組み立てで消え、誤りを返す代わりにプロセスを止めるからです。

## 何を確かめるか

| 領域 | 不変条件 | 破れると |
| --- | --- | --- |
| 値 | 値の幅より上のビットは、a 語でも b 語でも 0（wide.h） | 比較、縮約、表示が黙って誤る |
| 未来のイベント | イベントのヒープが（時刻、領域、通し番号）の順を保つ。時間の輪の件数が中身と一致する。今より前のイベントが無い | イベントの順が狂う、取りこぼす |
| プロセス | 手放した記録は終了済みで、それを指す今の番号の項目は待ち行列に無い（古い項目は出番まで残ってよい）。実行時に作った未終了のプロセスの数が正しい。待ち場所は 1 つまで | 再利用した記録が古いイベントで起こされる |
| 購読 | スロットや名前付きイベントの待ち手のうち今の番号のもの（プロセスの待ちの番号を持つもの）は、終了していないプロセスを指す | 古い起床 |
| NBA | 生きているイベント制御の数が Active の記録の数と一致する。時間スロットの終わりに、Ready または実行中の NBA は無い | 記録の漏れ、二重の解放 |
| ヒープ | 各プールで、空き場所は重複せず空で最後の世代より前にあり、それ以外の空の場所は引退済みで、空の場所に印は無い | 漏れ、解放後の使用 |
| 活性化レコード | 生きている数、リースの数、語数が記録の合計と一致し、空きの鎖は手放した記録だけを1 度ずつ持つ | 古いフレームの読み出し |

記憶域は要素へのポインタを渡すので、値の検査は、スケジューラがスロットの変化をそれを見ているものに知らせる
所で行います。何も見ていないスロットは確かめません。

## どうやって

- **実行時の切り替えではなく、組み立ての選択肢。** CMake の選択肢 `KIRIMASIM_DEEP_CHECKS` を、Debug のプリセット
  （dev、asan、ubsan、tsan、fuzz）で有効、release で無効にします。検査は、コンパイル時の定義から
  kernel の非公開のヘッダが決める定数に対する `if constexpr` で書くので、どちらの組み立てでも
  コンパイルされます。環境変数は読まず、書き換えられる大域の状態もありません。
- **違反は値。** Context が最初の違反（検査の名前と、見たもの）を記録します。スケジューラは次の安全な所で
  `EndReason::Internal` と `deep check <名前>: <内容>` で実行を終え、driver はそれを内部エラー、終了コード 3 として
  報告します。kernel の境界を越える例外はなく、強制終了もしません。
- **どこで。** 時刻を進めるたび、その時間スロットのすべての領域が空になった所で、未来のイベント、プロセスと
  その待ち、NBA の記録、ヒープのプール、活性化レコードを確かめます。実行の最後に時刻を進めようとして先に何も
  ない所でも、もう一度確かめます。値の検査は上に書いた所で行います。
- **正しい実行から見えるもの。** 何もありません。検査は読むだけで、PerfCount が読む数を数えず、結果を変えません。

## テスト

- Debug のプリセットでは、既存のテストがすべて検査つきで走るので、テスト全体が検査の答え合わせになります。
- 検査ごとに、それが守る不変条件を破る誤りを `tools/mutants.py` に置き、テストがその検査を通して失敗することを
  確かめます。
- 今の時点で検査に引っかかるテストは、kernel の不具合を示します。直す前に、検査の文言とともに報告します。

## 順番

1. 選択肢、Context の記録とその報告、値と未来のイベントの検査。
2. プロセスと購読。
3. NBA、ヒープ、活性化レコード。

それぞれ 1 コミットとし、誤りの注入と、Debug の組み立てでの自前のテストの時間（前後）を付けます。
