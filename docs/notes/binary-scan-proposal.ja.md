# バイナリ入力書式の修正案

[English](binary-scan-proposal.md)。状態：**承認済み（2026-10-23）**。
[SYSTEM_TASKS 6.3](../spec/SYSTEM_TASKS.ja.md#63-読み込み)と
[SIR_SPEC 8](../spec/SIR_SPEC.ja.md)へ反映しました。共通カーネルへ実装し、40プログラム・17,120変換と継続・拒否の検査で確認しました。

SYSTEM_TASKS.md 6.3のP1の対象には入力がありますが、従来のSIR_SPEC.md 8は
`%u`・`%z` を明示的に未対応としていました。今回の承認でその仕様上の制限を除きます。
IEEE 1800-2023 21.3.4.3とTable 21-7を確認しましたが、一般的なフィールドの
規則とのすべての関係が明示されているわけではありません。実装前に次の規則が承認されました。
規格本文と例は転載せず、独自の言葉でまとめています。

## SYSTEM_TASKS.md 6.3とSIR_SPEC.md 8への承認済み修正

- `$fscanf`・`$sscanf` の `%u`・`%U`・`%z`・`%Z` を、SIRで表現できる整数・
  列挙型・packedの集まりの代入先に対応させます。`$value$plusargs` の変換集合は
  21.6のまま変えず、unpackedの集まりも引き続き未対応です。
- 幅を省略すると代入先のビット幅を32ビットのワードへ切り上げて読みます。
  正の幅を指定した場合は転送するビット幅とし、その幅の上を落としてから、通常の
  ゼロ拡張・切り捨て・4値から2値への変換で代入します。幅0は既存の読み取りと同様に
  省略として扱います。幅の規則はTable 21-7に明記されたものではなく、比較実測も
  踏まえた本仕様の決まりとして承認されました。
- 代入を抑止する `%*u`・`%*z` は出力引数を取らずに消費します。省略時は32ビット、
  明示した幅があればそのビット数とします。これは本仕様の決まりです。
- ワードは下位から、各ワードはホストのバイト順で読みます。`%u` は32ビットの値、`%z` は
  VPI形式の値とマスクの組です。承認済みの出力符号化を逆にたどります
  （SYSTEM_TASKS.md 3.11、規格21.2.1.1・21.3.4.3・38.15）。
- **承認済みの解釈：** バイナリの変換では先頭の空白やNULを飛ばさず、データとして
  読みます。packed値を `$sscanf` で読む場合も同じです。書式自身の空白は従来どおり
  次の変換の前で読み飛ばします。従来のSYSTEM_TASKS.md 6.3は先頭の空白の例外を
  `%c` だけとしているので、生の転送を優先する旨を追加します。
- フィールドが全部読めた場合だけ代入します。不足した場合は出力先を保ち、
  実際に読めたバイトを消費し、ファイルではEOFを立て、読み取りを止めます。
  戻り値はそれ以前の代入数で、それ以前に変換がなければ `-1` です。
  成功した抑止変換はEOFの判定では変換に数え、代入数には数えません。
  途中のフィールドを代入しないのは本仕様の決まりです。
- 完全なフィールドの直後を先読みせず、必要なバイトだけを消費します。
  次の通常文字や変換はその直後から続け、ファイルの既存のpushbackも使えます。
- 定数・実行時の書式は共通カーネルの意味を使います。frontが代入先の幅を渡し、
  他の入力書式と同じく、成功した出力だけを書き戻します。ソースの文字列の書き換え、
  比較相手に特有の条件分岐、既定の言語の受理規則の緩和は加えません。
- 既存の実行期待値を緩めません。`%u` が未対応であるユニットテストは、対応する
  パーサー・型・消費バイト・値を積極的に確認するテストに置き換えます。
  既存のスイートの期待値は保持し、境界幅、X/Z、抑止、各バイトでのEOF、継続、
  入力の格納場所、呼び出し場所の検査を追加します。

幅と途中EOFの規則は、確定したIEEEの文言としてではなく、本仕様の選択として
明示しています。この意味の修正とP3・P4の範囲変更は、両方とも2026-10-23に承認されました。

## 比較用ツールの実測

自作の入力と実行結果だけを確認しました。コンパイラとランタイムの表示は
`14.0 (devel) (s20260301-411-gca6b8d376)` です。正確な13.0の動作は未確認です。

- 33ビットの代入先は `%u` で8バイト、`%z` で16バイトを消費しました。
- 32・65ビットの代入先への `%4u` は4バイトを消費して下位4ビットだけを保持し、
  `%4z` は8バイトを消費して値とマスクの4ビットだけを保持しました。
  `%*u` は4バイト、`%*z` は8バイトでした。
- 先頭の `20`・`09`・`0a`・`0d`・`00` のバイトはデータとして保持されました。
- 32ビットの代入先で `%u` に0～3バイト、`%z` に0～7バイトだけを与えると、
  `-1` を返して初期値の `deadbeef` を保ち、読めた分を消費してEOFが立ちました。
  全部読めた場合は1を返し、次の読み取りが末尾に当たるまでEOFは立ちませんでした。
- **承認済みの幅0の規則との差：** Icarusの `%0u`・`%0z` は `-1` を返し、代入先を
  保ち、データを消費せず、EOFも立てませんでした。上の案の省略時と同じ扱いとは
  異なります。この実測との差を含め、幅0を省略と同じにする選択が承認されました。

全観測と承認済みの本仕様の規則との比較は、次で再現できます。規格適合の判定ではありません。

```sh
python3 tools/binary_scan_probe.py \
  --kirimasim build/dev/src/driver/kirimasim \
  --output build/binary-scan-observations.json
```

自作の448ケースは、6種類の代入先幅、両書式、幅の省略・0・明示、NUL・空白、
書式中の空白、抑止、選択した不足フィールドの各バイトを含みます。完走した実行では
448件の識別子つき観測があり、候補規則との一致は374件、74件の差はすべて幅0でした。
ただし、その後のまとめた実行では、観測を出す前の異常終了もありました。
インストール済みの `s20260301-411-gca6b8d376` はSIGTRAP、既存の `f190dbb` は
SIGSEGVでした。原因は未確認で、調査のためにIcarusのソースは読んでいません。
ツールはネイティブの失敗と未完了の比較を明記します。

幅0を含めない部分は、別途測定しました。

```sh
python3 tools/binary_scan_probe.py \
  --kirimasim build/dev/src/driver/kirimasim --exclude-zero-width \
  --output build/binary-scan-nonzero-observations.json
```

この実行では選んだ374件すべての観測が得られ、候補規則との差はありませんでした。
レポートには除外した74件も記録します。実装前のkirimasimは書式を拒否し、観測は0件でした。
実装後は本仕様の448件すべてと一致し、幅0を除く比較でも両ツールの374件すべてが一致しました。警告や失敗の行を別のケースの結果として取り違えず、観測0件を
比較の成功として扱いません。

確認した版は[IEEEの公式ページ](https://standards.ieee.org/ieee/1800/7743/)のものです。
比較結果は相手の動作の証拠であり、規格の解釈を正当化する根拠そのものではありません。
