# 方向付き MOS ソースと通常の物理ドライバの接続

[English](source-mos-execution.md) が正。Status: 部分実装の確認点、2026-10-26。
MOS/switch 契約全体と P1 は未完成。

## 根拠と範囲

`e7e2ec59` で、slang のエラボレーション結果の `nmos`・`pmos`・`rnmos`・
`rpmos`・`cmos`・`rcmos` を、既存の
[強度網の SIR と共有カーネル](strength-network-execution.ja.md)へ接続した。
根拠は承認済みの [MOS/switch 契約 1/6/7](mos-switch-proposal.ja.md)、
[規範的な対応](p1-execution-contracts-2026-10-25.ja.md)、SIR_SPEC 3.5/5/7/10、
IEEE 1800-2023 4.9.5/28.7/28.8/28.10/28.13/28.16。
実装とテストは独自に作り、他のシミュレータの実装・テストは読まず、規格の本文や
例も写していない。依存、外部ツール、ABI、GC safepoint、PerfCount 予算、
formatVersion は変えていない。tier 1 は引き続きカーネルの C++ API を直接呼ぶ。

今回の範囲は、対応する4値整数の構造的データネットと通常のデータ式、固定した
スカラー出力端子（プリミティブ配列から slang が作るスカラー要素を含む）、
捕捉するデータ添字・制御、スカラー MOS 遅延。入力選択には packed window、
固定 unpacked 配列、既存の対応するネット全体のポート別名を使える。
式の入力は通常の strong のキャリアを使い、構造的ネット選択は公開した区間を読む。
無効な捕捉添字は、従来どおり全ビット幅を検査して X とする。

MOS/switch 全体への対応ではない。受動網と world solver、部分・非結合ポートの
同一性、登録したネットの force/release、全区間の `%v`、将来の VPI 強度参照は
未完成である。固定配列の既存ドライバ取り込み制限（unpacked 配列出力の三状態
side 解決など）も明示的な拒否を保つ。端子の合法性は固定版 slang が判断し、
メタデータ導入で診断を緩めていない。

## 一つの変換規則と一つの公開処理

`Lowerer::lowerMos` は二つの continuous process に分ける。捕捉側は既存の
ソースの暗黙の感度規則で制御式・データ式・添字を評価し、所有する型付き値を隠し変数に
保持する。純粋なデバイス側はそれらと構造的データ区間を読み、`strength.mos` を
実行して、所有するスカラー origin に `strength.drive` または
`strength.drive.delay` で書く。データの強度だけの変化では、制御関数、副作用、
RNG 呼び出しを繰り返さない。通常の依存が変われば必要な捕捉を行う。呼び出した関数の
暗黙の感度の規則は変えない。

`prepareStrengthNets`、既存のスカラー・固定配列の resolver 生成、
`finishStrengthNets` が、通常の実際の寄与を取り込む。生成途中の従来 resolver の
型付き入力 tuple から、私有のドライバ値・静的強度・任意の side を得る。
記録した process ID の処理を純粋な寄与アダプターへ変え、公開済みの解決結果を
物理的な根へ戻さない。関係しないネットは従来の経路を保つ。登録した物理スロットの
全ビット・全要素に node を置き、ネット全体を一つの component としてまとめて
公開する。このまとめ方は受動接続や world の相関を表すものではない。

暗黙の pull/supply は一度だけ実体化し、core のネット種別を正規化する。
書かれないビットは物理 origin の数に入れない。新しい MOS origin は Z で始まり、
通常の origin は初期 X と静的強度を保つ。従来未解決だった単独の三状態ドライバには
validity ビットが必要になる。未使用の side が初回伝播前の X を消してはいけない。
遅延付きゲートでは既存の値・side の pending tuple と validity を同時に commit する。
既に解決していた従来 tuple の side 初期値はゼロのまま保つ。メタデータ読み込みで
観測可能な解決を行わず、初期処理も共有スケジューラの Active queue を使う。
登録したネットに書けるのは component の公開処理だけである。

別名経由を含め、登録したネットへの force は hold 接続ができるまで位置付きの
unsupported 診断とする。カーネルと verifier の迂回書き込み禁止も保つ。
症状・ファイル名の認識やソース文字列の書き換えは導入していない。

## テストと参照実行の観測

独自ジェネレータ `tools/gen_source_mos_matrix.py` の **154 設計**を追加した。
期待値は承認済み契約に従って符号付きの強度点を列挙して計算する。AI が起案した
oracle であり、人が個別に確認したテスト標本ではない。軸は全6種類、
weak/pull/strong/supply と対向負荷、module/generate/interface の所有、幅
1/9/65/129、プリミティブ配列とネット全体のポート、降順・二次元 unpacked データ、
X/Z/桁あふれを含む129ビットの捕捉添字、式キャリア、通常・既に解決した入力の全4種の
三状態ゲート、初期 side、慣性遅延、暗黙 root、制御呼び出し回数と通常イベントを伴う
強度だけの変化。追加のツール検査6件は force・別名 force・受動接続・書式の境界と、
slang の端子診断の位置を確認する。既存29ダンプと PerfCount を含む278件が通った。

[コンパイルできる故障11件](../measurements/2026-10-26/source-mos-controls.json)を
新テストの実際の失敗で検出した。出所・感度の欠落、種類の間違い、添字の破棄、
取り込む強度・side・初期状態の誤り、遅延の破棄を含む。最初の2件はループ変数の
未使用警告でコンパイルが失敗したので、検出とは数えない。修正版はコンパイル後に
テストが失敗した。変異したソースをバイト単位で復元し、全CIの前に、記憶域の幅の追加3件を含む281件が通った。

[Icarus 比較記録](../measurements/2026-10-26/source-mos-icarus.json)は、独自154設計を
**Icarus Verilog/runtime 13.0 `v13_0-dirty`** で実行し、実行ファイルのハッシュも
記録する。全件コンパイルでき、113設計の標準出力が完全一致、41設計に差があった。

- データ選択36件は、129ビットの packed 位置の桁あふれで差が出る。こちらは X、
  参照はビット0の値になる。承認済み契約に従い、全幅の添字検査を保つ。
- 遅延初期状態3件は、明示的に承認された新規 MOS の Z、通常ドライバの初期 X、
  従来 side-mask の初期値による差である。提案はこれらの選択と参照観測を区別する。
- `notif0` の遷移2件は、無効→L→完全 X の順序で差が出る。
  [短い独自観測](../measurements/2026-10-26/source-mos-transition.json)にも、射影が X の
  まま区間だけが変わる場面を記録した。承認規則では対向負荷付き MOS 出力を X に
  更新するが、参照は0を保つ。参照実装内部の原因は **未確認**。記録したソースを
  実行し、先行状態や fanout を変えて確認できる。

差は観測として残し、oracle の変更で消していない。この有限行列で Icarus 全体との
同等性や P1 完成を証明したとはしない。外部 sv-tests・母集団の新しい基準値、Linux・
最小コンパイラ、5シミュレータの速度比較を今回測り直したとも扱わない。

## 検証と承認待ち

[全 local CI 記録](../measurements/2026-10-26/source-mos-validation.json)の21項目は、
**17成功・4構成のテスト項目が失敗**。dev・ASan・UBSanは5,361/5,364、releaseは
5,362/5,365が通る。各構成の失敗は `cli/options` だけで、既知スキップは
`cb/input_sample_1step` と `nets/net_port_drivers_part` の2件。新規154設計と境界6件は
全構成で通る。Werrorビルド、既存dump・PerfCount、方針検査、自動生成したREADME数値、
clang-format、全107ソースのclang-tidyは通った。自動期待値検査はupstreamなしで比較対象が
ないが、手動の `e7e2ec59^..e7e2ec59` は既存期待値保持として通る。

既存nmos拒否入力は無出力で正常終了するが、[厳密な期待値移行案](mos-expectation-migration.ja.md)の
承認待ちなので、古い拒否診断3件を保っている。確認済み・未適用のパッチは入力75個をすべて
保ち、ジェネレータの受理集合と、受理一覧・3診断だけを変える。別の人の承認と `src/` を含めない
コミットが必要で、**このレビューが解決するまでCIは緑ではない**。
この作業からイベント命令単位safepointの承認は推定しない。

[通常経路の重点測定](../measurements/2026-10-26/source-mos-speed.json)は全CI終了後に
releaseの `faadf4b7` と `e7e2ec59` を、20万回・交互5組、小さい実行の起動時間を差し引いて
比較した。frame accessは0.385017→0.372855秒（−3.2%）、event bounceは
0.077907→0.078514秒（+0.8%）。全カウンタは一致。RSS中央値はそれぞれ
9.203125→9.265625 MiB、9.203125→9.1875 MiB。負荷のある機械での観測であり、
安定した高速化・悪化の証明や7夜の基準値ではない。両設計はソースMOSを使わず、
新しい強度網・ソースMOSの負荷は未計測。予算や警告閾値は変えず、従来の時間記録も別実行として扱う。
