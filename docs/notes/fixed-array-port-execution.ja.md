## 契約と実装

2026-10-25に[固定配列ポートの契約1–6節](fixed-array-ports-proposal.ja.md)が承認され、
[詳細仕様への対応](p1-execution-contracts-2026-10-25.ja.md)を記録しています。
IEEE 1800-2023の7.6、23.3.3.2–7、SIR_SPEC 3.5/10とVALUE_SEMANTICS 5の規則を
自分の言葉で要約したものです。他のシミュレータの実装・テストを読まず、外部の着想、
新しい依存・インストール・大域状態も追加していません。

`Lowerer::mergePorts`が互換性のあるネット配列全体を同じ実体に結びます。
SIRの`Slot.viewOf`は宣言ごとの範囲・次元・要素型を保持し、宣言順の通し番号で
同じカーネルの格納先を指します。多段の接続も、先行する実体を直接指します。
VMは明示された数値の対応を実行し、ソースの形から意味を判断しません。
負の添字、広い値、X/Z、範囲外は各ビューで判定してから通し番号を求めます。
読み書き集合は実体の番号に正規化します。整数配列の定数要素・packed範囲への
force/releaseもこの実体を使います。スカラーのポートforceと明示的な配列aliasの制限は維持します。

`lowerPorts`は既存の`assignAggregate`・`copyArrayStorage`・`flushStores`を使い、
全RHSの捕捉後に代入します。範囲が異なっても宣言順で対応し、整数・real・shortreal・
stringが連続更新します。module/interfaceの起源とprogramのReactive側の起源を維持します。
配列の条件式はブロック引数で合流し、既知なら片側、X/Zなら両側を評価して、
値の共通規則で要素を合成します。階層名の固定型への問い合わせは値を評価せず宣言型を使います。
未接続の既定値は定義スコープでエラボレーションされた式を使います。
`unconnected_drive`は整数入力netの各要素をpull強さで駆動する暗黙プロセスを1本作り、
変数への警告と型の既定値は従来どおりです。

`Lowerer::resolveArrayNet`はvalsemで意味を定めた既存の`resolve`命令を要素ごとに使い、
各ドライバの強さを保ちます。私有領域は実際に覆う要素だけを持ち、`driverElements`が
実体の通し番号に対応させます。初期値は駆動ビットがX、未駆動ビットがZで、
packed部分書き込みの範囲も保ちます。tri0/tri1・supplyの既存の規則を要素ごとに適用し、
定数要素の慣性遅延は既存の`drive.delay`範囲で表します。ネットごとに解決プロセスを1本作り、
要素ごとの利用者プロセスやRNGは作りません。262,144要素のネットに対し、
1要素ずつを駆動する64ドライバの私有領域が64要素分であることを検査します。
検証器は実体、形、駆動範囲の順序、値のドメイン、書き込み集合、別名を通るuwire競合を検査し、
要素数の積のオーバーフローも拒否します。

SIR形式は0のままで、追加メタデータは`view-of=%sN`・`driver-elements=[...]`と決定的に出力します。
既存の形式0ダンプは変更していません。C ABIとカーネル公開ヘッダの変更は不要で、
ABIは0.3、第1層はC++ APIを直接呼びます。

## 検証と参照実装の観測

[独自の生成器](../../tools/gen_fixed_array_port_matrix.py)は358ソースを作り、宣言順・
ビットの駆動範囲・強さの優先関係から期待値を求めます。参照実装の出力を期待値には使いません。
SIRの4テストは独立した2つのContext、65ビット、不正・循環ビュー、範囲、uwire競合を確認します。
[境界検査](../../tests/tools/check_fixed_array_port_boundary.py)は疎な確保、enum・packed構造体のビットforce・型問い合わせ8通り、5種類の拒否を確認します。
選択した364テストが全件通過しました。その後の型問い合わせ・forceの拡張も通過します。
8種類の誤りを実際にコンパイルして入れ、84・3・125・108・48・9・4・1件の失敗で検出し、復元後も同じ検査が通過しました。
登録済み536個の負の対照の置換位置もすべて適用可能です。

幅1/8/65/129、二状態変数・四状態net、範囲と方向の違い、二次元、module/generate/interface、
programの領域、入力変数の連続更新、出力コピー、inout共有、多段別名、force/release、
型付き入力、条件式の捕捉、部分書き込み、pull、既定値、wired論理、慣性遅延を含みます。
元の提案59ソースは51件がモデルと一致し、7件は従来どおり違法な入力として拒否し、
1件の部分配列ポートは引き続き未対応です。

Icarus 13.0と開発版でも358件を再実行し、それぞれ184件一致、152件相違、22件コンパイル失敗でした。
相違は明示的な入力変数の再評価96件、共有netの強さ48件、supply配列8件です。
承認済みの契約に対する観測であり、参照実装の不具合を確定したとは扱いません。
型付き入力・program・forceには合法でも参照側でコンパイルできない例があります。
これらに合わせて期待値を変えていません。既存の87プローブでは`fixed_array_ports`と
`resolved_net_array`だけが新たに通り、各参照版が通る未対応例は24→22件になりました。
既存native成功例の判定対象バイトと参照側の全状態は不変で、参照の結果相違は4件／7件です。
固定した344件のsv-testsは244成功、P1母集団は1,451/1,466成功・失敗0・未対応15で不変です。
Linuxは再測定していません。

## 残る制限

部分配列のポート、refポート、構造体・オブジェクトなどの要素の所有は残作業です。
二状態netの明示宣言とchandleポートに対するslangの診断は維持します。
複数ドライバと合流するネット配列の三状態sideは位置付きで拒否します。
実行時に移動する駆動範囲は有効化しておらず、確認例はslangも非定数のnet代入先として拒否します。
範囲外の解決ドライバも未対応です。明示的な配列alias、unpacked net宣言時の初期化、
スカラーのポートforceは従来の診断を維持します。P1完了とは扱わず、他の承認済み契約と
機能・外部インターフェースの棚卸しも引き続き実装・検証が必要です。
