# NBAの保持値と保留中の発行順

[English](event-nba-payload-foundation.md)。状態：2026-10-27、main `1650064d`を基にした
未コミットの条件式対応と同じローカル作業へ実装しました。共有kernelの前提部分であり、
**ソースからのイベント制御付きNBAの対応ではありません**。P1は未完です。

## 承認済み契約と境界

根拠は[承認済みevent-NBA契約](event-nba-proposal.ja.md)のscheduler 4/5と値の生存期間、
[P1契約の対応表](p1-execution-contracts-2026-10-25.ja.md)、SCHEDULER_SPEC 3/8/13/14、
RUNTIME_ABI 6です。IEEE 1800-2023 4.6・4.9.4・10.4.2・10.6.2を背景とし、保留中の
発行順は承認済みのプロジェクト方針です。参照実装も同じ順とは主張しません。外部の実装・
再現コード・規格例は読まず写していません。依存追加、期待値の移行、仕様や性能予算の変更はありません。

C++20の公開`nba.h`とscheduler APIで、捕捉とready化を分けます。

- `captureNba(origin, writes)`はslot・要素・ビット範囲と値の語列を順にコピーし、
  発行番号と発行元のgroupを記録します。検証・確保が済んでからticketと`nba.scheduled`を
  公開します。有効な対象が空でも扱えます。不正な選択のleafは呼び出し側が省き、制御登録自体は残します。
- `readyNba(ticket)`でNBA/Re-NBAへ確定します。ready化した呼び出し元にgroupや順序を
  決めさせず、プロセスの再開・生成、子の追加、RNG seedの取得もしません。確定したticketの
  破棄・二重ready化は禁止します。空なら更新イベントを作らず完了します。
- `discardNba(ticket)`で未確定の保持値を一度だけ解放します。Context内のIDと周回しない
  世代で再利用を検査し、値・記述子のバッファを解放して小さな行を再利用します。ticketはContextより長く保持できません。

kernelがコピーするのはdomainの語であり、ソース言語のオブジェクトではありません。
実行層が型付きの独立したsnapshotを用意し、`visitPendingValues`で未確定・確定・実行中の全leafを
slotの型の識別とともに公開します。語を推測でheap handleとは扱いません。プロセスへのpointerを
保持せずgroupを捕捉するため、プロセス記録の再利用後も値を保てます。ただし、callback元の
frame・scope・RNGの保持はまだ接続していません。今後のイベント登録が承認済み契約に従って別に所有します。

`enqueueNba`は通常の即時NBAと発行カウンタを共有します。新しく発行した通常更新は従来どおり
O(1)で末尾へ追加します。古い保持値がreadyになったら、同じgroupの未適用の新しい更新より先に
挿入します。参照アルゴリズムによってActive/Reactiveへ移動済みの部分も対象です。適用済みの更新は
並べ直しません。slot開始時に期限となった時間指定更新は、元の発行時刻と独立に従来の優先度・順序を
保ちます。以前のslotで発行した制御も、readyになった時点で現在のready順へ入ります。両groupの領域は分離したままです。

値を適用する間も全体をrootとして保ち、leaf順に通常のslot書き込みを呼びます。guard callbackが
表を拡大しても、次のleafは表への借用参照でなく安定したticketで取得し直します。実行中の値は
callbackから破棄できません。hold/forceは既存の規則を使います。終了要求なら残るleafを適用せず、
quiescentでも未確定値を破棄して実行を引き延ばしません。final中や終了要求後の新規捕捉は禁止します。
公開カウンタ、C ABI 0.3の入口、SIR命令、formatVersionは追加しません。

## 独立した検証

新しい`NbaPayload`単体テストは**24件**です。両group、逆順ready、既定60周で独立したモデルと
比較する3,840発行（nightlyのfuzz倍率/seedにも対応）、NBA実行中のready化、前slotでの捕捉、
期限到来の優先度・適用済み更新を戻さない順序、発行元の終了/kill/記録再利用、世代、確定ticketの
破棄禁止、leaf順、129bitまでの語境界と4値の両面、変数全体へのforce/release、空の値、
正確なrootと実際のheap回収、再入での表拡大、不正入力、program/final/終了、200周の行再利用、
Context分離を検査します。確保失敗では部分root・書き込み・カウンタ公開・確保byteの漏れがないことを
確認し、発行カウンタの純粋な演算は上限直前と不正な0からも検査します。

[コンパイルした10故障](../measurements/2026-10-27/nba-payload-controls.json)を実テストで
検出します。snapshotの欠落、groupの喪失、ready順の使用、移動済み部分の無視、leaf逆順、
root漏れ、確定後の取消、行の未再利用、カウンタ周回、quiescent時のroot残留です。元のソースを
byte単位で戻し再ビルドしてから正常系を確認します。登録の文字列照合は検出に数えません。
最後の復元ビルドが完了する前に実行した確認結果は破棄し、完了後の再実行だけを採用します。
既存ソース・期待値・PerfCount値は変更しません。

## 残作業

frontは引き続きイベント制御付きNBAを未対応と診断します。持続するslot/named/式の購読、
通知の識別・合流、ソース順のguard、任意幅のrepeat回数、依存先の付け直し、一括登録が残ります。
発行元終了後のcallback元/frame/RNGの保持、型付き`nba.event` SIR、verifier/text、機械的なVM
転送も必要です。保持値だけを言語対応やIcarusとの差分の解消とは扱いません。既存の標準ライブラリの
領域dequeで起きるホスト確保失敗はready化時に捕捉しますが、Context PMRによる決定的な失敗注入の
対象にはなっていません。Icarus全機能の対応は未確認です。

## 計測を受けたイベント領域の修正

[初回の配置](../measurements/2026-10-27/nba-payload-initial-validation.json)も全CI 21件と
コンパイルした10故障の検査は通りましたが、[50万更新の一括発行](../measurements/2026-10-27/nba-payload-burst-initial.json)で
peak RSSが74.59→82.92 MiB（約11.2%増）となりました。全イベント記録に発行番号の語を追加する
必要はないため、通常NBAでは既存の種類別generation領域を発行番号に使うよう修正します。
保持値のイベントはそこに世代を置いたまま、世代を検査した保持行から発行番号を取得します。
期限到来の更新とNBA以外のイベントは現在の発行順ソートの対象にしません。callbackを借用せず、
順序を保って従来のイベント記録の大きさへ戻します。初回の計測・ハッシュは過去の証拠として残し、
最終配置の検証と計測は下に別に記録します。

## 最終配置のイベント領域の計測

[修正版の50万更新一括発行](../measurements/2026-10-27/nba-payload-burst-benchmark.json)は、
独立に定めた最終値の期待値に対して両binaryを各5回実行しました。peak RSSは
74.6094→74.5469 MiB（比率0.9992）、
simulation時間の中央値は0.08298→0.08422秒です。
全sampleが最後に発行した値と一致し、イベントの語の再利用により初回配置で観測した保留キューの
メモリ増加を解消しました。局所計測であり、7晩の基準や普遍的な速度を主張する値ではありません。
