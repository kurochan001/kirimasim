# P4 性能プロファイル（段階 A）

[English](p4-performance-profile.md) · 英語版が正本です。

2026-11-27 に `main` の 0.3.0（`b1ad0cb96a40`）で測定しました。
ロードマップの見直しに向けた計測と対照実験の記録です。

## CoreMark の結果

設計ごとに RTL とファームウェアをそろえ、1 反復を実行しました。Ibex は
**433,198 サイクル**、CVA6 の `cv32a65x` 合成ビューは **1,051,805 サイクル**で完走しました。
各実行で CRC 5 個（`e9f5`、`e714`、`1fd7`、`8e3a`、`e714`）とファームウェアの終了コード 0 が一致しました。
CVA6 の結果は上流が指定した合成除外を適用した構成に対するものです。

| 設計と実行条件 | キャッシュ準備後の中央値（秒） | µs／シミュレーションサイクル | ホスト実行命令数／シミュレーションサイクル |
| --- | ---: | ---: | ---: |
| Ibex・2 値 native | 10.625 | 24.53 | 503,199 |
| Ibex・4 値 native | 10.726 | 24.76 | 509,467 |
| Ibex・Verilator 5.054・P3 の設定 | 0.1097 | 0.253 | 6,492 |
| Ibex・Verilator 5.054・公式ガイドの設定 | 0.1105 | 0.255 | 6,492 |
| CVA6 合成ビュー・2 値 native | 344.794 | 327.81 | 6,115,450 |
| CVA6 合成ビュー・Verilator 5.054・P3 の設定 | 0.8635 | 0.821 | 21,927 |
| CVA6 合成ビュー・Verilator 5.054・公式ガイドの設定 | 0.8383 | 0.797 | 21,443 |

Ibex の 2 値 native は P3 の Verilator 設定に対して **1.033% の速度**で、経過時間は約 **97 倍**、
ホスト実行命令数は **77.5 倍**でした。4 値から 2 値に替えて減る実行命令数は **1.2%** です。
CVA6 合成ビューの 2 値 native は同ホストで P3 の設定に対して **0.250%** でした。

P3 の Verilator は `--binary --timing --threads 1 --top-module top -Wno-fatal` を指定しました。
[公式ガイドの速度向け設定](https://verilator.org/guide/latest/simulating.html#benchmarking-optimization)は
`-O3 --x-assign fast --x-initial fast --no-assert` を加えます。同じバージョンとホストコンパイラで
両設定を別途ビルドし、組にして比較した中央値は、P3／ガイドの順に Ibex が **0.1448／0.1475 秒**、
CVA6 が **0.8820／0.8792 秒**でした。ホスト実行命令数は Ibex でほぼ同じ、CVA6 で **2.2% 減**です。
Ibex の経過時間は同じ測定内の設定差より、測定回を替えたときの変動が大きくなりました。
ガイドの設定は未知値とアサーションの扱いを変えます。この比較で照合したのはファームウェアの出力と終了サイクルです。

### 測定条件

Apple M5 Max（18 コア、128 GiB）、macOS 27.2.1 arm64（26B131）。本体は Apple Clang
21.0.0（clang-2100.4.1.1）の Release で、`-O3 -DNDEBUG -ffp-contract=off` です。
生成 C++ は同じコンパイラで `-std=c++20 -O2 -fPIC -shared -fno-exceptions -fno-rtti
-ffp-contract=off -fno-fast-math`、今回ビルドした Verilator の生成コードは同じコンパイラと
既定のホットコード向け `-Os` を使いました。時刻計測はコンパイルとキャッシュ準備後に順序を変えながら
各モードを 5 回実行し、中央値を求めました。集計用カウンタと CPU サンプルは別に採取しました。
各実行の前後について 1・5・15 分負荷平均を記録しました。CoreMark の時刻計測中の 1 分負荷平均は
2.71〜7.31 でした。

P3 の保存 SIR・ファームウェア・比較用実行ファイルを再利用しました。Ibex の RTL 入力 **37 ファイル**は
OpenROAD `404977691e84` の `flow/designs/src/ibex` とすべて Git blob ID が一致しました。
P3 の記録で Ibex に付いている `a9adcf481395` は訂正が必要です。CVA6 は合成除外を適用する前の

元の CVA6 は `3a389af15180` です。ファームウェアのソースは Ibex `041098fe2380` です。

ファームウェア SHA-256 の先頭は `6af83d1f86eec882`、保存 SIR は Ibex が
`dc4dfdc469330447`、CVA6 が `66ca4d5a645f500a` です。
CVA6 では上流の `translate_off/on` と `HPDCACHE_ASSERT_OFF` を適用し、タイムスケールを

## 1 サイクルあたりの処理

アイランド内の生成 C++ 呼び出し数と VM 進入数の和は、各条件で `island.member_evals` と一致しました。
下表の生成割合の分母はこの値です。アイランド外で動いた生成本体は別途数えています。
`wait.subscriptions` は既存の購読を再利用した論理上の登録も含み、NBA 由来の実行イベントは
キュー上で連続分をまとめても論理上の更新件数を数えます。

| 1 シミュレーションサイクルあたり | Ibex native 2 値 | Ibex native 4 値 | CVA6 合成ビュー native 2 値 |
| --- | ---: | ---: | ---: |
| アイランドのメンバー評価 | 301.19 | 300.87 | 779.87 |
| メンバー評価で生成 C++ に入った割合 | 100% | 100% | 4.16% |
| スロット書き込み／値変化 | 983.96 / 463.54 | 972.75 / 457.99 | 1,656.36 / 565.51 |
| NBA の発行 | 41.98 | 41.98 | 286.16 |
| 待機の購読登録 | 1,157.61 | 1,154.98 | 2,275.85 |
| プロセス・アイランドの起床 | 156.00 | 155.43 | 52.41 |
| Active／NBA 由来の実行イベント | 156.00 / 41.98 | 155.43 / 41.98 | 52.41 / 286.16 |
| タイムスロット | 2.00 | 2.00 | 2.00 |
| VM で実行した SIR 命令 | 54.82 | 54.82 | 19,503.75 |

**CPU プロファイル。** キャッシュ準備済みの通常実行に `sample` を 1 ms 間隔で使い、
`Scheduler::run` 以下のスタックを数えました。Ibex は各状態モードで 5 秒ずつ 3 回採取しました。
CVA6 は完走中の 4 区間（開始から 12・110・210・305 秒の各 5 秒）を下表に集計しました。
別に採取した先頭 25,000 サイクルでも、打ち切り時のバス読み書き件数を Verilator と照合しました。
`time -lp` のプロセス全体の実行命令数には起動も含まれます。下表の標本比率とは別の指標です。
NBA の適用は、命令バイトが一致するデバッグ行番号付きの再リンク版で `Scheduler::execute` 内の位置を照合しました。
オフセットが省略されたり、複数の経路が合算された標本には、この方法で NBA と判別できないものがあります。

| スタック先頭の分類 | Ibex 2 値（11,471） | Ibex 4 値（11,484） | CVA6 2 値（15,186） |
| --- | ---: | ---: | ---: |
| アイランドのスケジューリングと待機処理 | 32.7% | 32.0% | 14.7% |
| 書き込み・通知（下段に帰属した NBA 適用分を除く） | 25.7% | 23.8% | 8.7% |
| 生成 C++ | 16.8% | 16.5% | 0.4% |
| NBA 登録 | 1.2% | 1.2% | 0.6% |
| NBA の適用のうち判別できた箇所 | 2.2% | 2.5% | 1.1% |
| VM インタプリタ | 4.5% | 6.3% | 59.2% |
| VM の再開・呼び分け | 2.8% | 3.1% | 3.3% |
| 時刻スロット・リージョンの進行 | 1.5% | 1.5% | 0.3% |
| その他 | 12.7% | 13.1% | 11.6% |

Ibex の 2 値 native では、スタック内に `evaluateIsland` がある標本は **61.3%**、
NBA 適用と判別できた標本は **2.2%** で、和集合は **63.5%** です。
生成 C++ の総呼び出し 155,158,525 回にはアイランド外の 24,684,622 回が含まれます。
VM の全 SIR 命令はテストベンチの 4 プロセスに帰属し、`top.always1`（RAM とファームウェア I/O）が
19,417,512 命令、`top.always0`（クロック）が 4,331,987 命令でした。アイランド外の
インタプリタ自身は CPU 標本の **2.6%** です。テストベンチが発生させたカーネル処理の時間は、
この値にまとめて含めていません。

CVA6 では CPU 標本の大半がアイランド内の VM 実行です。完走時の内訳では、生成を拒否された
198 プロセスが **112.6 億 SIR 命令**、同じアイランドの別プロセスが原因で生成できなかった
10,648 プロセスが **70.7 億命令**でした。上位は
`top.dut.issue_stage_i.i_issue_read_operands.gen_asic_regfile.i_ariane_regfile.always_ff0`（13.35 億）、
同 `always_comb0`（12.85 億）、`top.dut.issue_stage_i.i_scoreboard.always_comb2`（11.95 億）で、
いずれも拒否理由は `process-frame` です。最大アイランドには拒否理由が `instruction store` の
`top.dut.$port.cvxif_resp_i` や、`process-frame` の `top.dut.i_frontend.always_comb1` が含まれます。
同じフォールバックに複数の拒否メンバーが関与するため、妨げたメンバーごとの重みは重複します。
独立したコールバックの VM 命令は全体カウンタだけに現れる場合があります。

Ibex と代表 6 回路に強連結成分（SCC）はありませんでした。CVA6 の SCC は 4 個で、メンバーは
21、29、45、2,136 個です。成分ごとの反復履歴がリセットまたは終了する際の最終反復を一時計装で集計しました。
CVA6 の完走で **10,440,440 履歴**を記録しました。反復数の中央値は **4**、95 パーセンタイルは **12**、最大は **25** でした。
この計装版は別のビルドに置き、時刻比較から外しました。
[理由別件数と SCC の分布](../measurements/2026-11-27/p4-coremark-profile.json)

## 代表回路と Icarus との比較

固定入力のマニフェスト `befffe9069ef` と RTL のハッシュを照合しました。同じ保存 SIR で N=1
と表の N を各 5 回、順序を替えて実行しました。秒数の Δ はそれぞれの中央値の差です。
カウンタとホスト命令数は差を N−1 で割りました。N の単位は回路によりサイクル、トランザクション、
フレーム、刺激の反復です。時刻スロット数とリージョン別イベント数もデータに収録しました。
代表回路の時刻計測中の 1 分負荷平均は 3.43〜7.31 でした。

| 回路 | N | 4 値 VM／native の Δ（秒） | native のホスト命令／増分 | native のメンバー評価／書き込み／NBA |
| --- | ---: | ---: | ---: | ---: |
| `nba_shift` | 1,000,000 | 6.119 / 2.509 | 72,257 | 17 / 83 / 81 |
| `comb_chain` | 3,000,000 | 2.138 / 1.022 | 10,374 | 8 / 13 / 0 |
| `hierarchy_fanout` | 100,000 | 2.991 / 2.735 | 631,072 | 384 / 513 / 0 |
| `bus_fabric` | 150,000 | 0.481 / 0.355 | 60,741 | 52.1 / 57.1 / 1 |
| `uart_loopback` | 20,000 | 0.203 / 0.160 | 204,042 | 83.5 / 154.5 / 66 |
| `gate_udp` | 400,000 | 2.752 / 2.229 | 89,321 | 51.8 / 53.8 / 0 |

0.2.2 と同じ Icarus 14.0 開発版（`1eba369`）の時間を VM と native の時間でそれぞれ割ると、
`bus_fabric` は **0.88 倍／1.19 倍**、`uart_loopback` は **0.90 倍／1.14 倍**、
`gate_udp` は **1.04 倍／1.28 倍**でした。最初の 2 回路では、VM のホスト命令数は
Icarus より **31%**、**22%** 多く、native ではいずれも Icarus との差が **1.1% 以内**でした。
この 2 回路の native は、アイランド・待機・書き込み・通知に
標本のそれぞれ **61%**、**33%** を使っています。UART にはフレームあたり 240 SIR 命令と
36 タイムスロットも残ります。ゲート／UDP は native が Icarus より速い一方、この 4 処理で
標本の **82%** を占めます。

`nba_shift` の native では、NBA の登録と判別できた適用で CPU 標本の **44%**、生成 C++ は **8%** でした。
`comb_chain` では生成 C++ が **4%**、VM インタプリタが **32%** です。刺激を与える
`initial0` が 1 反復につき 32 SIR 命令を実行します。`hierarchy_fanout.initial0` は native でも
1 反復あたり 1,811 SIR 命令が残りました。
別途 `kirimasim-tests` の `06f00049d0ee` の全 28 回路を `+n=200` で実行し、VM と native の標準出力が一致しました。
14 回路で生成 C++ の呼び出しが 0 回で、生成拒否も 0 件でした。これらの頻繁に動く手続きは、
待機を含む `initial` や通常の `always` など現行コード生成の対象外です。
[代表回路のデータ](../measurements/2026-11-27/p4-daily-profile.json)

32 ビットの xorshift と積算だけを `initial` で回す対照では、2 値・4 値とも
**SIR 1 命令あたり約 130 ホスト命令**でした。N=1 と N=2,000,000 はどちらも
タイムスロットが 1 個で、両条件の命令数の差から求めました。この命令の組み合わせでは
VM の値演算と記憶域アクセスの費用も含めて測りました。
[インタプリタの対照データ](../measurements/2026-11-27/p4-fused-controls.json)

## 融合した C++ の対照実験と見積もり

手書き C++ と 2 値 native で、N=1 と表の N の最終チェックサムが一致しました。
シフトレジスタでは次のレジスタと積算値を別の領域に作り、エッジごとに一括で切り替えました。
組み合わせ回路は同じ刺激とチェックサムで 8 段を依存順に評価しました。Ibex の対照は
`mcycle_counter_i` の 3 本の 64 ビットコピー（SIR のプロセス ID は 831、832、828 の順）を
3 メンバーのアイランドとして切り出し、合成した入力を与えました。Apple Clang 21 の
`-O2 -ffp-contract=off -fno-fast-math` でビルドし、各条件 5 回の中央値の差を使いました。
対照は汎用イベントキューと中間信号の観測を省いた局所モデルです。

| 対照 | 2 値 native／手書き C++ の Δ（秒） | 1 増分あたりのホスト命令数 |
| --- | ---: | ---: |
| `nba_shift`（N=1,000,000） | 2.396 / 0.00639 | 72,081 / 114 |
| `comb_chain`（N=3,000,000） | 0.956 / 0.00545 | 10,289 / 27 |
| Ibex のカウンタ出力コピー（N=2,000,000） | 0.506 / 0.00365 | 7,639 / 6 |

これは局所で省ける仕事の目安です。例えば Ibex の小回路では、中間のコピーを C++ コンパイラが
除去できます。Ibex 全体については、アイランド評価と判別できた NBA 適用の **63.5%** を
すべて取り除き、他の費用が同じと仮定すると上限は **約 2.74 倍**です。
対象部分だけを 2 倍速くする仮定なら **約 1.47 倍**です。CPU 標本比を経過時間比とみなした
見積もりであり、実装後の性能や小回路の命令数比を CoreMark に当てはめた値ではありません。

## 再現と確認事項

準備済みの成果物を受け取る再実行コマンドは次のとおりです。ファームウェアのハッシュ、
CRC 全項目と最終サイクルを各回の実行で照合します。CVA6 は `cva6` と対応する合成ビューを渡します。
`--reference` の代わりに `--verilator-args=PATH` を使うと、そのファイルを基準にしたソースの順序と
オプションを JSON 配列から読み、Verilator 5.054 の両設定をビルドしてから実行します。

```sh
python3 tools/coremark_profile.py ibex --kirimasim build/release/src/driver/kirimasim \
  --sir "$IBEX_SIR" --firmware "$COREMARK_HEX" --reference "$IBEX_VTOP" \
  --out build/p4-ibex-replay --diagnostic
python3 tools/p4_profile.py --stdout build/p4-ibex-replay/diag-native-2.stdout \
  --tier build/p4-ibex-replay/native-2.jsonl --islands build/p4-ibex-replay/native-2.islands
```

スタック標本は同じ SIR・ファームウェア・状態モードの別実行で採ります。キャッシュ準備後の実行に
`sample <PID> 5 1 -mayDie -file stacks.sample` を接続し、採取したファイルを
`p4_profile.py --sample` に渡します。`--nba-sites` はバイナリごとに照合したオフセット一覧です。
今回の一覧は CoreMark の JSON の `nba_mapping.nba_offsets` にあります。

**仮説への回答。** Ibex ではイベントを処理する経路が大きな割合を占めます。
テストベンチ側の VM は Ibex では小さいものの、`comb_chain` と `hierarchy_fanout` では重要です。
CVA6 の VM 負荷の中心は、生成できなかった RTL です。生成された関数の本数だけでは、
この三つの違いを判別できません。

**未確認。** 関数別に正確な実行命令数は取れていません。関数別は CPU スタック標本で、CVA6 は完走中の 4 区間を抽出しています。
Linux x86-64 の実機で `perf` の命令カウンタとファームウェアの区間別プロファイルを取ると、
別環境で分布を確認できます。C ABI 呼び出しだけの独立した費用は、値とイベントの効果を保持した
対照実装で切り分ける必要があります。手書き C++ は複数の費用を同時に取り除いています。

**人が決めること。** 取得、ファームウェア、RTL の準備手順とアダプターはローカルにあります。
今回の再生スクリプトは準備済み入力で実行し、比較用の両設定をソースからビルドしました。
取得からの公開手順に組み込める素材の範囲は確認待ちです。速度の関門や仕様の改訂案は段階 B で扱います。
