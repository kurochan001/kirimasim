This document holds the rules for developing kirimasim together with AI. It restates the design specification's "policy for AI development".

## Principles

- Most of kirimasim's code is generated by AI (Claude Code). Humans are responsible for the specifications, the tests and the review. The README says so too.
- AI implements from the specifications. When a change would contradict a specification, a human approves it first as a change to that specification, before it is implemented.
- The shortcuts AI tends to take (C++ features that are banned, rewriting expected values, and the like) are stopped by automatic checks in CI rather than left to human review.

## Marking commits

- A commit made with AI carries the trailer `Assisted-by: <tool>:<model and version>` (for example `Assisted-by: Claude Code:claude-opus-5-5`).
- `Signed-off-by:` is not used: the project does not run the DCO, and pull requests are turned off (`CONTRIBUTING.md`).
- `Co-Authored-By` is not used for AI.

## What humans hold

Humans decide the following; AI only proposes.

- The specifications (`docs/spec/`)
- The expected values of tests (for the test suite, AI drafts them against the clauses of the standard, and a human approves the procedure and the results in batches; the `:spec_check:` field of a test says whether a human checked that test itself; TEST_SUITE.md)
- The performance budget (the expected values and thresholds of PerfCount)
- Adding a new dependency
- Adding global state, and adding an entry to `tools/global_state_allowlist.txt` (RUNTIME_ABI.md 9.3, 9.4)
- Text that is published

## Rules that protect expected values

- A change that alters, removes or loosens an expected value of an existing test goes in a commit separate from changes to the implementation. So does a change that gets the same effect by deleting or replacing the body of an existing test.
- New tests with their expected values, and new PerfCount items, may go in an implementation commit; a human checks their grounds.
- A change of an expected value states its reason and the clause of the standard, and a human approves it.
- CI judges each pushed commit by its own difference (`tools/check_expected_change.py`), and a pull request, should one be opened, by the difference from the merge base of base and head to head.

## Record of human contributions

How the law treats what AI generates differs from country to country and is not confirmed, so the history shows where a person's decisions and work are.

- **Decisions on the specifications:** the commit that records a person's approval of a specification, or of a change to one, carries the trailer `Approved-by: <name> <noreply address>`. The status line of the document stays as it is: the date and "approved".
- **Review:** when a person has read a commit made with AI before it is pushed, the commit carries `Reviewed-by: <name> <noreply address>`. A commit without it has not been read line by line by a person.
- **What a person writes:** a commit that a person wrote without AI carries no `Assisted-by` (the converse of "Marking commits"). When a person and AI both wrote one, its message says which parts the person wrote.
- **`:spec_check: human`:** the commit that turns a test's `ai` into `human` lists the tests checked and carries `Reviewed-by`. The header of the tests does not change. The number sampled and the errors found are reported at the end of P1, as TEST_SUITE.md says.

## Clean room

- The AI that implements is not given the source code of Icarus Verilog or Verilator to read, or any other source code under the GPL or LGPL (any version), and it does not port such code. Behavior is written into the specifications from the standard and from results of runs, and the implementation is made from those specifications. This procedure is kept on record.
- Only ideas are taken from elsewhere, and their sources are limited to papers, official documentation, the discussion in issues, and design notes written by people that contain no code. Code quoted in any of these is not taken. When such an idea is used, the design note says where it came from: the section of `docs/spec/` that uses it names the source, and a longer note goes in `docs/notes/`.
- Tests are treated the same way: the reproducing code of other projects' issues and their test suites are not copied; the test is written anew from what the bug is.
- The text, figures and example code of the standard are not copied: only references by clause number and summaries in our own words.

## Contributions from outside

- For now, only specification proposals and issues are accepted from outside; code pull requests are not (`CONTRIBUTING.md`).
- When code pull requests are accepted, they must disclose AI use, and a human must understand the contents and take responsibility for them (the same idea as LLVM's human-in-the-loop policy).

## What is not known

What has not been checked is written as "not confirmed", not filled in by guessing. Version numbers are the ones actually looked up.
