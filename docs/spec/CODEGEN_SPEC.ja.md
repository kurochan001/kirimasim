## C++ 生成の規則

残りは表の優先度のフェーズで書く。次の規則は 2026-10-19 に承認した。

- 同じ SIR からは、1 バイトも違わない同じ C++ を作る（NFR-6）。CI で 2 回作って比べる。
- `&&`、`||`、`->`、`?:` の短絡評価を保つ。SIR はそれを分岐で表し（SIR_SPEC.md の 5.2 節）、生成コードが論理演算をビット演算に変えるのは、右辺に副作用も null の参照も無いと証明できたときだけ。
- 副作用のある式は、SIR が示す回数だけ評価する。コードを複製するのは、副作用が無いと証明できたところだけ。
- VALUE_SEMANTICS.md の 3.1 節の左から右の順が、呼び出しの引数のように評価の順が決まっていない C++ の構文に出会うところでは、値をその順に一時変数に通す。

## 静的アイランド

最初の規則は 2026-10-19 に、残りは 2026-11-14 に承認した（[提案](../notes/static-islands-proposal.ja.md)と、その段階）。両方の層で対応する島を実行できる。`a4075801` から通常実行で既定で島を作る。

- 静的アイランドの中では、`analysis` が決めるレベル順に、各プロセスを 1 回ずつ評価する。第 1 層も島のプロセスに同じ順を使うので、タイムスロットの中で通る値（グリッチを含む）が、両方の層で同じになる。
- プロセスを島に入れるかどうかは、`analysis` だけが SIR から決め、解析の表に記録する（SIR_SPEC.md の 1 節、SIR v1 の提案の D6）。島の実行が変えるのは、メンバーを評価する時点と順序だけで、命令の意味は変えない。

### 候補と理由

- 候補は SIR_SPEC.md の 7.1 節が挙げるプロセス。種類が `cont`・`comb`・`latch`・`ff`・`ff-plain` で、遅延がなく、最初以外にイベント制御がなく、副作用のある呼び出しがないもの。
- 最初の版では、次のどれかの理由があるプロセスを島から外す。解析の表には、プロセスごとに、入った島か、外した理由コードを記録する。理由コードは変えない名前とする。あとで範囲を広げるときは理由を取り除く。範囲を狭めるのは期待値の変更になる。

| コード | 島から外す理由 |
| --- | --- |
| `kind` | 種類が上の 5 つのどれでもない |
| `delay` | 遅延がある |
| `mid-event-control` | 最初以外にイベント制御がある |
| `side-effect-call` | 副作用のあるサブルーチンを呼ぶ |
| `net-resolver` | `netResolver` の付いた `cont`（SIR_SPEC.md の 7.1 節） |
| `heap-value` | ヒープ上の値（文字列、動的配列、キュー、オブジェクト）を読み書きする |
| `system-task` | システムタスクを呼ぶ |
| `dpi` | DPI のサブルーチンを呼ぶ |
| `report-queue` | unique・priority の違反の報告や、遅延即時アサーションを積む（SCHEDULER_SPEC.md の 15 節） |
| `override-target` | 手続き的な `assign`・`force` の対象になりうるスロットに書く |
| `program` | program に属する |
| `scc` | 帰還を反復しない解析で、依存グラフの強連結成分に入る。通常実行では帰還の反復を有効にして解析する。 |
| `runtime-index` | 書く範囲か、感度として読む範囲に、実行時にしか分からない添字がある（UNSPECIFIED_BEHAVIOR.md A7 の反復を実装するまで） |
| `unknown-entry` | 解析の表の項目が欠けているか古い |
| `codegen-unsupported` | 第 2 層だけ：島に、第 2 層が生成できない命令がある。島ごと第 1 層の島実行で動かす |

### 依存グラフ、島、レベル順

- 依存グラフの節は、外されなかった候補。同じタイムスロットの中で、P が書くスロット範囲を Q が感度として読むとき、P から Q へ辺がある。範囲はビット単位で比べる（UNSPECIFIED_BEHAVIOR.md A7）。NBA による書き込みは辺を作らない。
- 島は、グラフの連結成分ごとに作る。同じトリガー（スロット、そのビット、エッジ）で起きる `ff`・`ff-plain` は 1 つの島にまとめる。
- レベル順は、グラフのトポロジカル順とし、同順位は SIR のプロセス番号順とする。同じ SIR と同じオプションからは、バイト単位で同じ表を作る。
- 対応する強連結成分は、両方の層で落ち着くまで `--max-scc-iter` を上限に反復する（UNSPECIFIED_BEHAVIOR.md A6、CLI.md の 2.6 節）。
- スロットの削除や畳み込みはしない。すべてのスロットが実体を持ち続ける。
- 解析の表の欠けた項目や古い項目は「不明」とし（SIR v1 の提案の D6）、そのプロセスは島に入れない（`unknown-entry`）。

### 第 1 層での島の実行

- 島は、実行カーネルに 1 つのプロセスとして登録する。メンバーは個別には登録しない（SCHEDULER_SPEC.md の 11 節）。
- メンバーが感度として読むスロット範囲のうち、島の外から書かれるものが変わったとき、または `ff`・`ff-plain` メンバーのトリガーが起きたときに起床する（SCHEDULER_SPEC.md の 4.3 節）。
- 1 回の起床で、入力が変わったメンバーと、その書き込みで入力が変わった下流のメンバーを、レベル順に各 1 回評価する。
- メンバーの本体は、島の外と同じく第 1 層のインタプリタで実行する。
- 最初の版では、島の中の書き込みも実行カーネルの通常の書き込みを通す。島の外で待つプロセス、波形、VPI のコールバックは、島なしと同じ経路で変化を受け取る。
- `ff`・`ff-plain` メンバーの NBA は、通常どおり実行カーネルに積む。同じトリガーで起きるメンバーは、待ち始めた順に評価する（SCHEDULER_SPEC.md の 4.3 節）。NBA の発行順は、島の有無で変わらない。
- 時刻 0 の手順は変えない（SCHEDULER_SPEC.md の 6.1 節）。
- 設計の実行中に、プロセスを島から外すことはしない。外す必要のある形は、上の理由で外しておく。
- 競合探索モード（`--race-check`）は、島の中の順序を乱さない（SCHEDULER_SPEC.md の 11 節）。
- `ff`・`ff-plain` を含む段階 3 の既定切替は 2026-11-23 に承認された。`--disable-pass=islands` で島を使わずに実行できる（CLI.md の 2.3 節）。

### 初版のアイランドの対象を広げるネイティブ実行

- 感度リストが固定でガードのない通常の組み合わせプロセスがトップレベルにある場合、その本体を生成できる。プロセスの識別子、最初に待つ時点、待ち直す時点、通知順での位置を保つ。生成できないときは同じ本体を VM で実行する。
- 複数の RTL 本体をまとめて生成できるのは、省く途中評価を観測できないと解析で確認できる場合に限る。時刻 0 の起動、クロックとリセットのエッジ、ブロッキング更新、NBA の順序、他のプロセスが読む値、ホストからの参照、診断と実行上限を含む。元の SIR と名前付きオブジェクトの識別子を保持する。解析で確認できない場合、または観測機能が証明の前提を満たさなくする場合は既存の実行経路を選ぶ。
- テストベンチと設計はいずれも入力から実行する。まとめて生成した領域を層間照合するときは、境界での書き込みと NBA、その順序、スケジューラの各境界で観測できる状態を元のプロセスと比較する。性能比較では、基準実行と同じテストベンチ、ファームウェア、状態数、該当するシミュレータオプションを使う。

### 通常の組み合わせ本体にある有界ループ変数

- トップレベルで感度リストが固定の組み合わせ本体では、入れ子のない有界ループの
  32 ビット 4 状態変数 1 個を、その本体の実行中に生成 C++ のローカルに置ける。
  解析では、別名、サブルーチン、感度リストによる参照を含め、そのスロットへの
  アクセスが本体自身に限られることを確認する。実行中は自身の待機が解除されて
  いることが必要。ほかに中間値を観測できる可能性があれば通常の書き込みを使う。
- 最適化を使う前に、今回の実行が条件を満たすことを確認する。グリッチ記録の設定が
  ある場合は、記録を開く前の起動時点も含めて通常の書き込みを使う。競合観測、
  VPI、保持中のスロット、または有効な観測者がいるスロットも同様。
- SIR スロットとその識別子を保持する。RUNTIME_ABI.ja.md の 4 節の集約操作で、
  本体が復帰する前に最終値を反映する。分岐のチェックポイント、他の書き込みと
  NBA の順序を保つ。最終値が初期値と同じ場合も、論理上の書き込み数と値の変化数を
  PerfCount に計上する。
- 層間照合では、最適化したローカル計算を VM の効果列と照合する。各カウンタ
  書き込みを元の位置で照合し、最終値と論理上の件数は反映時に別途照合する。

### 第 2 層の最初の版

- 最初の実装は島のメンバーだけを対象とした。現在は上記の固定感度プロセスも第 2 層で生成できる。残りのプロセスは同じ実行カーネル上の第 1 層で動く。
- 生成コードは、上の「C++ 生成の規則」と「浮動小数点」に従う。
- 第 2 層が生成できない命令を含む島は、島ごと第 1 層の島実行で動かし、`codegen-unsupported` を記録する。エラーにはしない。
- 4 状態モードでは、対応する島の入力が既知であることを確認できたときに、生成した 2 状態版の本体を使える。明示的な `--state=2` は実行全体で 2 状態近似を選ぶ。
- 島の中の評価の順と、各メンバーの評価の回数は、第 1 層の島実行と同じにする。
- `--tier-check` は、第 2 層の島の評価を 1 回ごとに第 1 層の島実行と比べる（CLI.md の 2.3 節）。生成コードの演算は `valsem` と突き合わせる（CLAUDE.md）。
- ドライバは生成した翻訳単位を独立した C++20 共有モジュールとしてビルドし、例外、RTTI、浮動小数点演算の縮約を無効にする。コンパイラの実行ファイル一つに引数を個別に渡す。生成モジュールはモデルの activation に渡された C 関数表を介してカーネルを呼ぶ。ドライバはエントリを登録する前に ABI 版、正規 SIR のダイジェスト、要求サービス、フレーム配置を照合する。未対応の本体があれば島全体を VM で評価する。
- キャッシュキーには RUNTIME_ABI 第 2 節の全項目を含める。ビルドごとにキャッシュと同じファイルシステム上に専用の一時ディレクトリを作り、完成したモジュールをアトミックに公開する。同時実行は完成済みの項目を再利用できる。ビルドが失敗した場合はモジュールを公開しない。

P2 の任意の解析表はスキーマ版 1 を使う。キーは SIR の形式版、末尾の LF を含む
正準 SIR 全体の SHA-256、スキーマ版、対象・レイアウトの識別子、版付きの生成器識別子、
生成器が定めた決定的なパス・オプションのバイト列の SHA-256 からなる。利用側は
現在の実行から期待キーを求め、設計のダイジェストを再計算する。未知の版、キーの
不一致、不正な ID・幅・依存順があれば表を破棄する。

値の行は対象の種類、本体の種類、行 ID、ブロック ID、命令の位置、値の位置の
順に並べ、重複を許さない。対象はスロット、ブロック引数、命令結果、SSA 値または
定数の被演算子で、幅、X が生じないという根拠、保存理由を持つ。アイランドの行は
プロセス ID 順に並べ、所属アイランド、レベル、整列済みの先行プロセス ID を持つ。
先行プロセスは同一アイランドの低いレベルに属する。表または行が欠けた場合は不明と
する。解析結果は SIR の外に置く。解析アルゴリズムと静的アイランドの適格判定は
P3 が行う。[検証付きのメモリ上のインターフェース](../../src/analysis/include/kirimasim/analysis/tables.h)
を使う。

## 浮動小数点

2026-10-19 に承認。

- **決まり：** 実行カーネル、VM、そのほかの kirimasim 自身のコード（`src/`、`tests/`）と、第 2 層が生成する C++ は、`-ffp-contract=off` を付け、`-ffast-math`、`-Ofast`、`-funsafe-math-optimizations` を付けずにビルドする（CLAUDE.md）。依存には課さない。数学の関数（`$sin`、`$exp` など）はシステムの libm に任せるので、最後のビットがシステムによって違いうる。これが実数についての NFR-2 の唯一の例外である。
- **理由：** IEEE 754 の倍精度である `real`（規格の 6.12）の式は、どの層と OS でも同じビットにならなければならない（NFR-2）。乗算と加算を 1 つの FMA の命令にまとめるコンパイラは、積を丸めずに足すので、2 つの演算を別々に行ったときと最後のビットが違いうる。まとめるかどうかは、コンパイラ、対象、フラグで変わる。
- **2026-10-19 に確かめたこと：** `double f(double a, double b, double c) { return a * b + c; }` を `-std=c++23 -S` で、`-O2` と `-O3` で翻訳し（2 つは同じ結果だった）、出力に FMA の命令（arm64 は `fmadd`、x86-64 は `vfmadd`）があるかを調べた。使った機械は arm64 の Mac で、ほかの対象は `--target` で翻訳しただけで、実行はしていない。

| コンパイラ | 対象 | `-ffp-contract=off` なし | あり |
| --- | --- | --- | --- |
| Apple clang 21.0.0 | arm64-apple-macos | FMA（`fmadd`） | FMA なし（`fmul`、`fadd`） |
| clang 22.1.8（Homebrew の LLVM） | aarch64-linux-gnu | FMA | FMA なし |
| clang 22.1.8（Homebrew の LLVM） | x86_64-linux-gnu | FMA なし（`mulsd`、`addsd`） | FMA なし |
| clang 22.1.8（Homebrew の LLVM） | x86_64-linux-gnu、`-march=haswell` | FMA（`vfmadd213sd`） | FMA なし |
| GCC 16（Homebrew） | arm64-apple-darwin | FMA | FMA なし |

- したがって、2026-10-28 まで `-ffp-contract` も `-march` も付けなかったプリセットでは、arm64（macOS と arm64 の Linux）向けのビルドはまとめ、x86-64 向けのビルドはまとめないので、`real` の結果が両者で違いえた。Apple clang は既定でまとめる（`__FP_FAST_FMA` を定義する）。2026-10-28 からは `CMakeLists.txt` が kirimasim 自身のコードに `-ffp-contract=off` を付け、`tools/check_release_flags.py` が、リリースビルドの `src/` と `tests/` のすべての翻訳単位にそれがあり、`-Ofast`、`-ffast-math`、`-funsafe-math-optimizations` のどれも無いことを確かめる。
- フラグを付けても、macOS arm64 の Apple clang 21.0.0 で、dev ビルドの 8,170 個のテストのどれも結果が変わらなかった（2026-10-28 に確認）。
- **未確認：** Linux の CI のジョブのコンパイラである x86-64 Linux の GCC と clang で、`-march` のあるときと無いとき（確かめ方：CI のジョブで同じ翻訳をする）。CI の macOS のランナー（`macos-26`）が arm64 か（確かめ方：CI のジョブで `uname -m`）。

## VM・生成 C++ 混在の実行基盤（P4）

P2 の SIR v1、既存カーネル ABI（`RUNTIME_ABI.ja.md`）、P3 の static island、`--tier-check` を出発点とし、P4 では以下の 2 つの代表例を通常の実行経路で動かせる最小の混在実行基盤を実装する（全 SIR 命令の AOT 化や UVM 全体の動作は必須に含めない）：

1. **待機をまたぐ VM・native 間の呼び出し：** 生成 C++ の呼び出し元から VM 側の待機付き `automatic` タスクを共通の 2 階層コールフレームチェーン経由で呼び出し、`#delay` やイベント待ちをまたいでローカル値を保持したまま中断・再開し、NBA を発行して呼び出し元へ復帰する。再開時刻、保持値、復帰時点、NBA の順序・結果が VM 参照実行と一致し、`fork` による多重同時待機でのフレーム独立性と、`disable` / `disable fork` による途中破棄時の安全な巻き戻し・リーク防止も満たすこと。
2. **中間信号の観測と従来経路へのフォールバック：** 将来の SVA や VPI からも利用できるよう、何をいつ観測するかを解析で明示する。観測者のない適格区間はまとめて評価し、静的観測者がある場合、実行時の `force`/`release` や VPI 介入がある場合、または同値性を静的に証明できない場合は従来経路を選び、4 値遷移とイベント順を保つ。
